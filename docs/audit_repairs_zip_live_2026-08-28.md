## Итог

**Находок 8: 5 серьёзных, 3 умеренных.** Все пять серьёзных — про одно и то же
место: **синхронизацию справочника оборудования**. По коду её никто не смотрел,
потому что к ремонтам и ЗИП она отношения будто бы не имеет. На живых данных

Главная находка — не производительность, а потеря данных на экране: **задача,

все четыре открытых ТО и несколько сотен осмотров. Причём исчезли они не
из-за сбоя, а наоборот — **после того, как синхронизация впервые за сеанс
успешно отработала**.

**Сам функционал ремонтов и ЗИП работает.** Всё, что удалось открыть, отработало
правильно, включая правки прошлых аудитов, — проверено вживую и перечислено в
разделе «Что проверено на устройстве и работает».

## Серьёзно

### 1. Задача исчезает из приложения, если её оборудование заархивировано

**Файлы:** `lib/src/tasks/equipment_list_screen.dart:66-90` (`_equipmentWithTasks`),
`lib/src/model/task.dart:14, 62` (`Task` хранит только `equipmentUuid`)

Список задач строится **от справочника оборудования**, а не от самих задач:

```dart
final equipment = GlobalState.dataProvider.inventoryRecords;
for (final item in equipment) {
  final tasks = _filteredTasksFor(item);      // getTasksForMachine(item.uuid)
  if (tasks.isNotEmpty) result.add((item, tasks.length));
}
```

Задача, чьего оборудования нет в локальном справочнике, не будет посещена
никогда — она просто не существует для экрана.

А в справочнике его может не быть законно. Эндпоинт `/v1/company/equipment/`
не отдаёт заархивированное интеграцией оборудование: на стенде это **6 529 из
11 529**, приложению видны 5 000. При этом осмотры на архивном оборудовании
сервер продолжает отдавать как ни в чём не бывало.

**Наблюдение на стенде.** Все четыре открытых ТО стоят на архивном
оборудовании:

```
 id  |              name              | integration_archived
1841 | Станок фрезерный №1500 (копия) | t
1843 | ваыва                          | t
1844 | DDSSDSDSD                      | t
1845 | ЦЦЦЦЦ                          | t
```

и вместе с ними ещё сотни осмотров («аимс» — 20, «Вентустановка №1024» — 40,
«DDSSDSDSD» — 41 и так далее). На экране «Задачи» при этом —
**«Нет активных задач»**.

**Самое неприятное — как это проявилось.** В 07:57 те же задачи были видны:
приложение работало на старом снимке справочника, снятом до архивации. В 17:13
`syncInventory` впервые за сеанс отработала успешно, сделала
`inventoryBox.clear()` и залила свежие 5 000 записей — **и все задачи на
архивном оборудовании исчезли с экрана**. То есть починка синхронизации ломает
список задач.

**Данные для показа у приложения есть.** Сервер присылает оборудование прямо
внутри осмотра:

```json
"equipment": {"id":1843,"uuid":"1a4b5aca-…","name":"ваыва","type_model":null}
```

но `Task.fromJson` берёт оттуда только `equipment_uuid`; название не
сохраняется, хотя `Task` — объект верхнего уровня, и дописать поле в конец
адаптера правилами проекта разрешено.

**Обходного пути нет.** Сканер ищет отсканированный QR в том же локальном
справочнике (`qr_screen.dart:141`):

```dart
for (var machine in dataProvider.inventoryRecords) {
  if (machine.uuid.toLowerCase() == barcodeUUID.toLowerCase()) { … }
}
```

Совпадения нет — цикл молча заканчивается, и **ничего не происходит**: ни
перехода, ни сообщения. То есть архивное оборудование недоступно тремя
способами сразу: его нет в «Задачах», нет в «Осмотре оборудования или ТМЦ», и
сканирование его QR не даёт никакой реакции. Заодно это отдельная мелкая
недоработка: незнакомый QR стоило бы отбивать сообщением, а не тишиной.

**Что делать.** Строить список **от задач**, а не от справочника:
 сгруппировать
задачи по `equipmentUuid` и брать карточку оборудования из справочника, а когда
её там нет — из самой задачи. Для этого добавить `Task.equipmentName` (в конец
`write()`, чтением через `try/catch`). Тогда задача на архивном оборудовании
останется видимой и закрываемой — вместе со списанием ЗИП, ради которого всё и
затевалось.

Отдельно стоит решить с заказчиком, **должны ли** открытые ТО переживать
архивацию оборудования. Если нет — это вопрос к бэкенду, и тогда правка на
клиенте становится страховкой, а не основным решением.

### 2. Справочник оборудования качается целиком на каждый `mainSync`

**Файлы:** `lib/src/data/data_provider_sync.dart:38-52` (`syncInventory`),
`lib/src/data/data_provider_remote.dart:26-48` (`loadAllInventory`),
`lib/src/data/data_provider_sync.dart:635-660` (`mainSync`)

```dart
var inventoryRecords = await loadAllInventory();   // все 5 000, 50 страниц
await inventoryBox.clear();
await inventoryBox.addAll(inventoryRecords);
```

Инкрементальности нет, ключи в боксе автоинкрементные (точечно обновить
запись нельзя), `clear()` + `addAll()` вместо «залить свежие, убрать лишние».

`mainSync()` вызывается фоновым циклом **раз в 60 секунд**, плюс на входе в
«Задачи», плюс после отправки осмотра.

**Сервер инкрементальный режим уже поддерживает** — тот же самый, что у ЗИП.
Проверено запросом:

```
GET /v1/company/equipment/?limit=2&updated_since=2026-08-28T00:00:00Z
→ {"items":[…], "deleted":[…6529…], "sync_until":"2026-08-28T16:47:29Z"}
```

То есть правка целиком на стороне клиента: повторить для оборудования то, что
уже сделано для ЗИП (`_syncSparePartsIncremental`), включая ключи по `uuid` и
флаг незавершённой записи.

Ирония в том, что в комментарии к `mainSync` этот урок записан прямым текстом —
но про каталог ЗИП:

> «Каталога ЗИП здесь намеренно нет. Он на порядок больше остальных
> справочников… любое действие обходчика — вход в „Задачи“, нажатие „Сканер“,
> отправка осмотра — тянуло весь каталог».

Каталог оборудования сопоставим по размеру и **тяжелее по трафику в 28 раз**
(см. находку 3), но остался полной перезаписью.

### 3. 96% трафика оборудования — QR-коды, которые приложение не использует

**Замер на стенде:**

| Справочник | Вес страницы (100 записей) |
| --- | --- |
| `spare_parts` | 53 КБ |
| `consumption_norms` | 48 КБ |
| **`equipment`** | **1 513 КБ** |

Разница не в количестве полей. В каждой записи оборудования едет отрисованный
QR-код картинкой:

```json
"qr_code": "data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAAAeoAAAI4CAIAAAAqET3U…"
```

**Доля `qr_code` в ответе — 1 447 КБ из 1 507 КБ, то есть 96%.**

Приложение это поле **не использует нигде**: `InventoryRecord.fromJson` его не
разбирает, и по всему `lib/` строка `qr_code` не встречается ни разу (единственные
совпадения — иконки `Icons.qr_code_*`). Обходчик сканирует физический QR со
шкафа; рисовать его на телефоне незачем.

Итого на полный проход: **50 страниц × 1,5 МБ ≈ 75 МБ**, из которых ~72 МБ
скачиваются и выбрасываются. При проходе раз в ~7 минут это порядка
**600 МБ в час** на телефоне обходчика.

**Что делать.** Находка 2 (инкрементальность) убирает это сама собой: после
первого прохода страниц почти нет. Дополнительно стоит попросить бэкенд не
класть `qr_code` в списочную схему — но это уже задача второго порядка.

### 4. Страница в 1,5 МБ против таймаута 8 секунд — проход рушится целиком

**Файлы:** `lib/src/http/api.dart:143-144` (`_readTimeout = 8 c`),
`lib/src/data/data_provider_remote.dart:26-48`

Живой лог с устройства:

```
SEVERE: DataProviderSync: Failed sync inventory:
        TimeoutException after 0:00:08.000000: Future not completed
  #2  DataProviderRemote.loadAllInventory (data_provider_remote.dart:33)
  #3  DataProviderSync.syncInventory (data_provider_sync.dart:42)
```

Одна страница весит 1,5 МБ, таймаут на запрос — 8 секунд. Запаса почти нет: на
свободном канале страница отдаётся за 1,6–2,8 с, но под нагрузкой (параллельный
проход, занятый сервер, сотовая связь в цеху) легко переваливает за 8.

**И тогда теряется весь проход, а не одна страница.** Цикл в
`loadAllInventory` не ловит исключение постранично и ничего не фиксирует по
ходу: 40 скачанных страниц (60 МБ) выбрасываются, `syncInventory` пишет
`SEVERE` в лог, бокс остаётся нетронутым. Через 60 секунд всё начинается с
нулевой страницы.

За время наблюдения это повторялось многократно; раздел «Задачи» показывал
спиннер или «Нет активных задач» **35 минут подряд**, до 17:13, когда проход
наконец уложился в таймаут.

**Что делать.** Находка 2 снимает и это: страниц становится единицы. Сверх
того имеет смысл ловить сбой постранично и фиксировать скачанное, чтобы
медленная страница стоила повтора страницы, а не всего справочника.

### 5. URL оборудования без завершающего слеша — 307 на каждой странице

**Файл:** `lib/src/http/equipment_api.dart:12`

```dart
'${API.baseUrl}/v1/company/equipment?limit=${limit}&skip=${offset}'
```

Слеша нет — FastAPI отвечает `307` и редиректом уводит на `/equipment/`.
Клиент редирект отрабатывает, поэтомуфункционально всё верно, но **каждая страница
стоит двух round-trip**. В логе бэкенда это видно парами:

```
"GET /v1/company/equipment?limit=100&skip=4900"   307
"GET /v1/company/equipment/?limit=100&skip=4900"  200
```

Замер: **2,76 с** без слеша против **1,63 с** со слешем — то есть лишние
~1,1 с на страницу, ~55 секунд на полный проход.

Это единственный такой URL в проекте: `consumption_norms/`, `spare_parts/`,
`fault_inspections/`, `repairs/` — все со слешем. Правка — один символ.

## Умеренно

### 6. У `syncInventory` нет защиты от параллельного запуска

**Файл:** `lib/src/data/data_provider_sync.dart:38`

У каталога ЗИП такая защита есть (`_sparePartsSync` — присоединиться к идущему
проходу), у осмотров есть (`_isSyncingScans`), у черновиков ремонтов есть
(`_isSyncingPendingRepairs`). У оборудования — нет.

Наблюдал на стенде два прохода одновременно: в логе бэкенда за одну минуту шли
две независимые последовательности `skip` — одна с 1100, другая с 4100. Это
удваивает и трафик, и время, и вероятность поймать таймаут из находки 4.

Возникает легко: фоновый цикл идёт своим проходом, обходчик заходит в «Задачи»
— экран запускает `syncMainOnce()` поверх.

### 7. Сбой синхронизации ничем не показан обходчику

**Файлы:** `lib/src/data/data_provider_sync.dart:47`,
`lib/src/tasks/equipment_list_screen.dart:106-126`

`syncInventory` при сбое пишет `SEVERE` в лог и молчит наружу. Экран в это
время показывает либо спиннер (если справочник пуст), либо устаревшие данные —
без единого признака, что синхронизация не удалась.

Обходчик 35 минут смотрел на крутящийся индикатор, не имея никакого способа
понять, что происходит и что делать. У очередей отправки такая связь уже
выстроена (полоса «Осмотры не отправлены», пометки об отказе) — у справочников
её нет.

### 8. ~590 МБ RSS во время прохода по справочнику

`loadAllInventory` копит все 5 000 разобранных записей в памяти, а до этого
каждая страница проходит через `jsonDecode` вместе с 1,4 МБ base64 на страницу.
Замер на эмуляторе: `TOTAL PSS 455 МБ`, `TOTAL RSS 590 МБ`.

Эмулятор это переживает. Бюджетный телефон обходчика — не обязательно: Android
убивает фоновые процессы задолго до таких цифр. Находки 2 и 3 снимают и это.
