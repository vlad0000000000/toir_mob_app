## Итог

**Новых находок 12: 3 серьёзных, 4 умеренных, 5 мелких. Из них закрыты 7 —
все серьёзные и все умеренные.**

Три серьёзных лежали в одном слое — **связка очередей и сетевого клиента**.
Прошлые аудиты разбирали каждую очередь по отдельности и каждый экран по
отдельности; всё, что найдено сейчас, жило на стыках: очередь наработки
блокировала очередь осмотров, список ремонтов не знал про очередь черновиков,
пять методов API не знали про общий клиент.

Ни одна из находок не была связана с правками М4–М15 — все они старше.

**Что осталось:** пять мелких (8–12). Ни одна не влияет на данные — это
механическая замена оставшихся `print`, порядок разбора ответа в
`updateUsageParameter`, мёртвое `??` в `InventoryRecord.copyWith`,
неиспользуемый импорт и тройной вызов в тернарнике.

**Чего эти правки не проверяли.** Всё сделано разбором кода и тестами; на
устройстве приложение не запускалось. Отдельно стоит проверить руками два
сценария, которые тестом не воспроизвести:

1. **Чтение наработки, сохранённой прежней версией приложения** — у неё в
   потоке нет поля `lastError`, и адаптер обязан прочитать её через `try/catch`
   как неотклонённую. Двух адаптеров с одним `typeId` в одном изоляте не
   зарегистрировать, поэтому старый формат в тесте не подделать. Схема ровно та
   же, что у `ScanAdapter` и `SparePartAdapter`, которые этот путь уже проходят
   в бою, и `UsageUpdate` нигде не вложен в другой объект — правило проекта
   соблюдено.
2. **Полоса и лист отклонённой наработки** — виджет-тестами не покрыты, как и
   остальной интерфейс приложения.

## Серьёзно

### 1. Неотправляемая наработка навсегда блокирует закрытие ТО вместе со списанием ЗИП

**Исправлено 27 августа 2026.** У `UsageUpdate` появилась пометка об отказе
(поле `lastError`, дописано в конец Hive-адаптера; ключ записи не изменился).
Очередь наработки классифицирует ошибку так же, как очереди осмотров и
ремонтов, отклонённую больше не повторяет, а шлюз закрытия ТО её не ждёт.
Отклонённая наработка видна полосой на главной, разбирается листом «Повторить /
Удалить».

**Файлы:** `lib/src/data/data_provider_outbox.dart:453-476` (`syncUsageScans`),
`lib/src/data/data_provider_outbox.dart:524-541` (шлюз в `_syncScansImpl`),
`lib/src/http/equipment_api.dart:107-140` (`updateUsageParameter`)

Осмотр задачи ТО намеренно ждёт, пока уедет наработка по тому же оборудованию:

```dart
final hasPendingUsage = scanUsageBox.values.any(
      (usage) => usage.equipmentUuid == scan.equipmentUuid,
    ) || scanUsagePendingBox.values.any(...);
if (hasPendingUsage) {
  continue;   // ТО ждёт наработку
}
```

Замысел верный: администратор должен увидеть наработку раньше отметки о ТО.
Проблема в том, **чего ждут**. У очереди наработки, в отличие от очередей
осмотров и ремонтов, нет понятия отказа вовсе:

```dart
} catch (e) {
  await scanUsageBox.delete(scan.key());
  await scanUsagePendingBox.delete(scan.key());
  await scanUsageBox.put(scan.key(), scan);   // назад в очередь. Всегда.
  _outboxLog.warning('наработка ... не отправлена, осталась в очереди: $e');
}
```

В модели `UsageUpdate` нет ни `lastError`, ни `isRejected` — ни одного поля,
которым можно было бы пометить «сервер отказал по существу». Любой ответ, кроме
успеха, приводит к повторной постановке в очередь.

`updateUsageParameter` шлёт `PATCH .../usage-parameters/{uuid}` с
`current_value`. Отказ по существу здесь вполне реален: значение меньше
предыдущего, параметр удалили на сервере (404), у обходчика отозвали права
(403). Ответ не изменится никогда.

**Что получает обходчик.** Он закрыл ТО с фактическим расходом ЗИП на пять
позиций. Наработка отклонена сервером навсегда. Каждые 5 секунд, весь день:
попытка отправить наработку → отказ → назад в очередь → осмотр ТО видит
непустой `scanUsageBox` → `continue`. **Осмотр не уйдёт никогда, ЗИП не
спишется никогда, и на экране об этом нет ни слова** — очередь ведь «не
отклонена», она просто ждёт. Кнопка «Повторить», которая есть у отклонённого
осмотра, здесь не появится: осмотр не помечен отказом.

Сравните с очередями осмотров и ремонтов: обе отличают временный сбой от
отказа по существу (`isRetryableScanError`, `isRetryableRepairError`), обе
ставят пометку, обе показывают её обходчику. Очередь наработки — единственная,
которая этого не умеет, и единственная, от которой зависит чужая очередь.

**Как проверить:** закрыть задачу ТО с наработкой меньше текущей и с расходом
ЗИП. Осмотр останется в очереди навсегда, счётчик «не отправлено» — тоже.

**Что предлагалось.** Дать `UsageUpdate` пометку об отказе по образцу `Scan`:
классифицировать ошибку (`isRetryableScanError` подойдёт как есть), при отказе
по существу записать причину и перестать долбить. Шлюз в `_syncScansImpl`
должен ждать только **неотклонённую** наработку — иначе один отказ парализует
второй конвейер. Отклонённую наработку показать там же, где отклонённые
осмотры.

### 2. Список ремонтов показывает черновик и созданный по нему ремонт двумя карточками

**Исправлено 27 августа 2026.** `_visibleDrafts` отсеивает черновики, чей
`serverUuid` уже есть в кэше ремонтов — тем же правилом, что и счётчик.
Пометку «Не отправлено» вместо спрятанной карточки несёт карточка самого
ремонта (`_RepairTile.queuedDraft`).

**Файлы:** `lib/src/repairs/repairs_list_screen.dart:172-198, 245-265`,
`lib/src/data/data_provider.dart:400-415`, `lib/src/data/data_provider_outbox.dart:69-88`

Конвейер отправки черновика состоит из трёх шагов: создать ремонт → загрузить
снимки → дописать расход и статус. После первого шага ремонт уже есть на
сервере и **сразу кладётся в кэш**:

```dart
final repair = await api.createRepair(...);
await upsertRepair(repair);                       // ремонт в repairBox
current = current.copyWith(serverUuid: repair.uuid);
await pendingRepairBox.put(current.localId, current);   // черновик остаётся
```

Черновик остаётся в очереди намеренно — снимки ещё не уехали. Если связь
оборвалась между шагами (ровно тот случай, который комментарий рядом и
описывает: «доехал ремонт, но не доехали снимки»), оба объекта живут
одновременно.

Счётчик активных ремонтов это учитывает — `_refreshActiveRepairsCount`
специально вычитает черновики, чей `serverUuid` уже есть среди активных:

```dart
final known = {for (final repair in active) repair.uuid};
final drafts = pendingRepairBox.values.where((draft) {
  final uuid = draft.serverUuid;
  return uuid == null || !known.contains(uuid);
}).length;
```

**А список — нет.** `_visibleDrafts` отдаёт все черновики без исключения,
`_visibleRepairs` — все кэшированные ремонты, и обе коллекции рисуются одна за
другой без какой-либо сверки.

Мало того, `_syncMyRepairsFull` **специально удерживает** такой ремонт в кэше,
чтобы он не пропал (`if (cached != null && cached.isActive) keep.add(uuid)`), —
то есть дубль не рассасывается сам, а гарантированно сохраняется до конца
отправки снимков.

**Что видит обходчик:** в списке ремонтов две карточки на один насос — «Черновик
· Не отправлено» и «Открыт», — а на плитке главного экрана написано «1». Открыв
первую, он попадёт в карточку черновика, открыв вторую — в карточку настоящего
ремонта; правки в них не связаны.

**Что предлагалось.** Отфильтровать в `_visibleDrafts` черновики, чей `serverUuid`
уже присутствует среди видимых ремонтов, — ровно тем же правилом, что и в
счётчике. Пометку «снимки ещё не ушли» уместнее показать на карточке самого
ремонта, а не отдельной карточкой черновика.

### 3. Пять сетевых вызовов идут мимо общего клиента — в том числе создание и правка ремонта

**Исправлено 27 августа 2026.** Все пять переведены на `_client`; в
док-комментарии клиента добавлено правило, запрещающее top-level `http.*` в
методах API.

**Файлы:** `lib/src/http/repair_api.dart:216` (`createRepair`), `:346`
(`claimRepair`), `:400` (`updateRepair`), `lib/src/http/task_api.dart:237`
(`addPeriodicTask`), `lib/src/http/auth_api.dart:74` (`login`)

В `api.dart` есть общий клиент, и его назначение описано там же прямым текстом:

```dart
/// Раньше каждый вызов шёл через top-level `http.get/post/...`, а они на каждый
/// запрос поднимают собственный `IOClient` ... некуда было поставить
/// `connectionTimeout` ... Теперь попытка соединения сдаётся за три.
final http.Client _client = _OfflineAwareClient(_newIoClient());
```

Все методы API ходят через `_client` — кроме пяти перечисленных, которые
по-прежнему зовут top-level `http.post` / `http.patch`. Переход, судя по
комментарию, был сделан, но эти пять вызовов пропустили: их легко не заметить
грепом, потому что записаны они переносом строки (`await http\n  .patch(`).

Последствий три, и они разной тяжести.

**а) Нет `connectionTimeout` — 3 секунды превращаются в 8.** Сеть есть, сервера
нет: SYN уходит в пустоту, ОС молча ретраит, и запрос висит до внешнего
`.timeout(API._readTimeout)`, то есть все 8 секунд вместо трёх. Именно ради
этого клиент и заводили.

**б) Окно недоступности не ставится.** `_OfflineAwareClient` при сетевой ошибке
зовёт `API.markServerUnreachable()` — 30 секунд, в течение которых остальные
запросы отказывают мгновенно, а цикл очереди отходит на бэкофф `[5, 15, 60]`.
Провалившийся `createRepair` этого окна не ставит: цикл продолжает будить сеть
каждые 5 секунд.

**в) Окно недоступности не снимается — и это самое неприятное.**
`markServerReachable()` вызывается только внутри обёртки. Успешный
`createRepair` или `updateRepair` её не проходит, поэтому:

> Сервер лежал, окно поставлено. Связь вернулась. Обходчик нажимает «Отправить
> ремонт» — `updateRepair` идёт мимо обёртки, честно достукивается до сервера,
> ремонт уходит. Окно при этом **остаётся стоять**. В ту же секунду очередь
> осмотров получает синтетический `SocketException('Сервер не отвечает,
> попытка отложена')` и откладывает отправку — по памяти, хотя сервер только
> что ответил.

Расходится это само через 30 секунд или на первом `isAlive()`, но полминуты
приложение противоречит самому себе.

`addPeriodicTask` в том же списке — это отправка заявки о проблеме, то есть
второй по важности пользовательский сценарий после осмотра.

**Что предлагалось.** Заменить `http.` на `_client.` в пяти местах. Правка
механическая, поведение методов не меняется. `login` можно оставить на
усмотрение — но и он выиграет от трёхсекундного таймаута соединения.

### 4. Округление количества пропущено на третьем экране расхода

**Исправлено 27 августа 2026.** `roundConsumptionQuantity` добавлено в
`_setQuantity` экрана конфликта.

**Файл:** `lib/src/qr/scan_conflict_screen.dart:339-362`

Правка М5 добавила `roundConsumptionQuantity` в `_setQuantity` карточки ремонта
(`repair_detail_screen.dart:793`) и формы осмотра (`result_controls.dart:237`).
Экран разрешения конфликта — третье место, где количества правят теми же
кнопками, — остался без неё:

```dart
void _setQuantity(int index, double value) {
  if (value <= 0) return;          // ← roundConsumptionQuantity нет
```

Шаг считает общая секция (`consumptionStep`), и для дробного количества он равен
0,1. Позиция из нормы с плановыми 0,25: одно нажатие «−» даёт
`0.15000000000000002`. `formatConsumptionQuantity` печатает такие значения как
есть, и это же число уходит на сервер в `actual_consumptions`.

Экран этот открывают именно тогда, когда сервер отказал по нехватке ЗИП, — то
есть в момент, когда количества правят чаще всего.

**Что предлагалось.** Добавить `value = roundConsumptionQuantity(value);` первой
строкой. Одна строка, тот же вид, что в двух других экранах.

### 5. Локальный остаток не уменьшается после успешного списания

**Исправлено 27 августа 2026.** После успешной отправки осмотра с расходом
`DataProvider.applyLocalStockWriteOff` уменьшает остатки и двигает
`sparePartsRevision`. Разбор строки расхода вынесен в чистую
`parseConsumptionWriteOff` и покрыт тестами.

**Файлы:** `lib/src/data/data_provider_outbox.dart:548-556`,
`lib/src/widgets/spare_part_consumption.dart:156-168`

При успешной отправке осмотра с расходом ЗИП сервер списывает позиции со склада.
Клиент об этом не узнаёт: в коде нет ни одного места, где локальный остаток
уменьшался бы. Каталог освежает только фоновая синхронизация — раз в 60 секунд
(`startSyncing`).

Внутри этого окна:

* раздел «ЗИП» и карточка позиции показывают остаток **до** списания;
* предупреждение о нехватке в блоке расхода считается по тому же устаревшему
  числу и молчит там, где должно сработать.

Сценарий: обходчик закрыл задачу, списав 8 из 10 болтов. Тут же открывает
вторую задачу на том же оборудовании и ставит 5 болтов. Баннера нехватки нет —
локально всё ещё 10. Осмотр уходит в очередь и возвращается отказом 409, а
разбирать его придётся на экране конфликта.

Тяжесть умеренная: окно короткое, данные не теряются, отказ обрабатывается
корректно. Но обходчик получает отказ там, где приложение могло предупредить.

**Что предлагалось.** После успешной отправки осмотра с непустым `actualConsumptions`
уменьшить остаток в `sparePartBox` по разобранным позициям и двинуть
`sparePartsRevision`. Значение всё равно перезапишется ближайшей
синхронизацией — локальная правка нужна только чтобы закрыть минутную дыру.
Альтернатива дешевле: дёрнуть `syncSpareParts()` сразу после успешного
списания.

### 6. Нехватка на складе не переспрашивается перед отправкой осмотра

**Исправлено 27 августа 2026.** Расчёт нехватки вынесен из `build` в общую
`consumptionShortages`; форма осмотра переспрашивает перед отправкой и
перечисляет позиции с остатком. Именно спрашивает, а не запрещает: без сети
остатки могли устареть.

**Файл:** `lib/src/qr/qr_result_screen.dart:737-790`

Перед отправкой приложение переспрашивает про **пустой** расход по настроенной
задаче (`skipsWriteOff`) — правильная и полезная проверка. Про расход, который
заведомо больше остатка, не переспрашивает ничего, хотя блок расхода прямо над
кнопкой уже рисует красный баннер «нет на складе».

Итог предрешён: осмотр уходит в очередь, сервер отвечает 409, осмотр помечается
отклонённым, обходчик идёт разбирать его на отдельный экран — и там нажимает
«Уменьшить до остатка», то есть делает то, что мог бы сделать на месте.

Жёстко блокировать отправку нельзя: без сети локальный остаток может отставать,
и приложение не вправе утверждать, что списание не пройдёт. Но подтверждение с
текстом «На складе меньше, чем указано. Сервер может отклонить осмотр.
Отправить?» — ровно тот же приём, что уже применён к пустому расходу.

**Что предлагалось.** Добавить второе условие в тот же `Dialogs.areYouSure`: если хоть
одна позиция расхода превышает локальный остаток — своё подтверждение. Данные
для проверки уже посчитаны в `SparePartConsumptionSection` (`shortages`), их
достаточно вынести в общую функцию.

### 7. Осмотр уходит без фотографии, если снимок не разобрался

**Исправлено 27 августа 2026.** Сбой декодирования прекращает отправку
исключением с внятным текстом; `syncScans` относит его к невосстановимым, и
осмотр остаётся в очереди с причиной вместо молчаливой потери кадра.

**Файл:** `lib/src/http/scan_api.dart:39-58`

```dart
try {
  final bytes = base64Decode(cleanBase64);
  ...
} catch (e) {
  print('Ошибка декодирования изображения $i: $e');
}
```

Снимок молча исчезает: запрос уходит без него, сервер отвечает 200, очередь
считает осмотр доставленным и удаляет запись. Ни обходчик, ни администратор
никогда не узнают, что кадр был.

Строка в базе Hive может испортиться (обрыв записи, урезанная строка), и это
единственное место, где такое обнаружилось бы.

**Что предлагалось.** Как минимум перевести на логгер уровня `severe` — сейчас это
`print`, который в релизе не соберёшь. Правильнее — не считать такую отправку
успешной: пусть осмотр останется в очереди с внятной причиной, чтобы обходчик
мог переснять.

### 9. `updateUsageParameter` разбирает тело до проверки кода ответа

**Файл:** `lib/src/http/equipment_api.dart:127-133`

```dart
final Map<String, dynamic> responseData = jsonDecode(responseBody);
if (response.statusCode != 200 && response.statusCode != 201) {
  throw Exception('Failed to update usage params: ...');
}
```

`jsonDecode` стоит **перед** проверкой и типизирован как `Map`. Ответ шлюза
502 с HTML-телом или JSON-массив вместо объекта дадут `FormatException` /
`TypeError` вместо заготовленного сообщения — то есть отказ придёт в очередь в
нераспознаваемом виде. Прямо связано с находкой 1: чем невнятнее исключение,
тем меньше шансов классифицировать его правильно, когда классификация появится.

### 10. `InventoryRecord.copyWith` написан так, будто у него есть параметр `hasOpenRepair`

**Файл:** `lib/src/model/inventory_record.dart:83-111`

второй из двух warning'ов анализатора (`dead_null_aware_expression`).

Данные это **не портит**: значение сохраняется. Но выглядит строка как рабочая

хотя по виду должен. Единственный вызов (`data_provider.dart:810`,

## Что проверено и оказалось верным

Чтобы не перепроверять это в четвёртый раз:

* **Hive-адаптеры ремонтов и ЗИП** — порядок чтения совпадает с записью во всех
  шести (`Repair`, `RepairConsumption`, `RepairNormItem`, `RepairPhoto`,
  `PendingRepair`, `SparePart`); хвостовые поля читаются только у объектов,
  лежащих в боксе самостоятельно. `PendingRepair` теперь закрыт круговым
  тестом через настоящий Hive.
* **Идемпотентность создания ремонта** — ключ берётся у черновика с самого
  начала, `serverUuid` записывается до загрузки снимков, повторный проход
  второй ремонт не создаёт.
* **Удаление черновика с уже созданным ремонтом** — спрашивается отдельным
  текстом, счётчик активных дедуплицируется. Список сначала не дедуплицировался
  (находка 2), теперь дедуплицируется тем же правилом.
* **Инкрементальная синхронизация каталога ЗИП** — откат на полный проход при
  отсутствии `sync_until`, курсор двигается последним, флаг незавершённой
  записи вокруг пары `clear()`/`putAll()`.
* **Классификация отказов осмотра** — «уже доставлен», «токен протух»,
  «временный сбой» и «отказ по существу» разведены и обрабатываются по-разному.
* **Защита от повторного ремонта** — четыре независимых признака, включая
  серверный `has_open_repair`, который единственный видит чужие ремонты.
* **Подбор позиции ЗИП** — дубли невозможны, уже добавленные погашены, поиск по
  локальному каталогу работает без сети.
* **Ограничитель ввода количества** — один разделитель, 9 цифр, 4 знака после
  запятой, ровно как `Numeric(14, 4)` на сервере.
* **Смена выбранной задачи обнуляет расход** — по uuid, а не по «есть/нет», так
  что переход между двумя задачами с расходом тоже очищает позиции.
