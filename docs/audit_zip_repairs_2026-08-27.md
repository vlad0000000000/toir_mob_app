## Серьёзно

### 1. `context.watch<DataProvider>()` не работает — провайдер не уведомляет

**Файлы:** `lib/main.dart:561`, `lib/src/data/data_provider.dart:42`,
`lib/src/qr/qr_result_screen.dart:659`, `lib/src/qr/qr_screen.dart:107`,
`lib/src/login/login_screen.dart:49`

`DataProvider` объявлен как `class DataProvider {` — не `ChangeNotifier`,
`notifyListeners` в нём нет вовсе. В дерево он положен обычным `Provider`:

```dart
MultiProvider(
  providers: [
    Provider(create: (context) => dataProvider),
  ],
```

Значит `context.watch<DataProvider>()` в трёх экранах **не перерисовывает
ничего** — подписываться не на что. Выглядит как реактивный код, ведёт себя как
`context.read`.

В нашей области это проявляется на экране результата скана. Каталог ЗИП
подгружается вызовом `ensureSparePartsLoaded()` в `initState`, причём без
`await` — экран строится сразу. Пока каталог не приехал:

* `_unitOf()` возвращает `null` → строки расхода без единиц измерения;
* `_stockOf()` возвращает `null` → **предупреждения о нехватке на складе не
  показываются вовсе**.

Когда каталог догрузится, `watch` не сработает, и экран останется в этом виде до
переоткрытия. То есть на первом холодном старте (и после любой чистки данных)
обходчик заполняет расход, не видя, что позиции на складе нет.

**Что предлагаю.** Либо `ChangeNotifierProvider` и `notifyListeners()` в ключевых
точках, либо — точечно и дешевле — `ValueNotifier` на каталог ЗИП по образцу
`activeRepairsCount` и `ValueListenableBuilder` вокруг блока расхода. Второе не
трогает архитектуру и закрывает конкретный вред. Заодно стоит убрать
`context.watch<DataProvider>()` из трёх экранов: он вводит в заблуждение.

### 2. Открытые списки не перерисовываются после фоновой синхронизации

**Файлы:** `lib/src/repairs/repairs_list_screen.dart:155`,
`lib/src/spare_parts/spare_parts_screen.dart:91`

Список ремонтов читает данные прямо из провайдера:

```dart
List<Repair> get _visibleRepairs {
  final statuses = _effectiveStatuses;
  final result = <Repair>[
    ...GlobalState.dataProvider.repairs.where(...),
```

Подписки на изменение `repairs` нет. Единственный реактивный элемент экрана —
плашка `_AuthExpiredBanner` через `ValueListenableBuilder`. Раздел ЗИП устроен
так же: отобранный список лежит в поле `_visible` и пересчитывается только
поиском, фильтром и жестом «потянуть вниз».

Поэтому пока экран открыт, до него не доходит **ничего** из происходящего в фоне:

* фоновый цикл синхронизации раз в минуту;
* доставка черновика очередью — ремонт стал настоящим, а в списке всё ещё
  черновик;
* инкрементальная синхронизация каталога — остатки в кэше обновились, на экране
  прежние;
* **SSE-сигнал `repair_changed`** — сервер специально шлёт его на каждое
  изменение ремонта, клиент честно перечитывает список по REST, и результат не
  виден. Механизм работает вхолостую ровно в том сценарии, ради которого
  задуман: администратор меняет ремонт, пока обходчик смотрит на него.

Это же объясняет «залипшую» подпись «Остатки на …»: строка считается в `build`, а
`build` не вызывается.

**Что предлагаю.** Один `ValueNotifier<int>` — ревизия кэша, — который дёргают
`upsertRepair`, обе синхронизации и очередь; экраны оборачивают список в
`ValueListenableBuilder`. Механика в проекте уже есть (`activeRepairsCount`,
`rejectedScansCount`), нужно распространить её на сами данные.

### 3. Отклонённый осмотр нельзя исправить — только повторить или выбросить

**Файлы:** `lib/src/qr/scan_conflict_screen.dart:421-435, 440-470`,
`lib/src/data/data_provider.dart:868`

Типовой сценарий: обходчик закрыл ТО в цеху без связи, указал расход 5 шт. Пока
осмотр лежал в очереди, позиции разобрали, на складе осталось 3. Сервер отвечает
409 `insufficient_stock`, осмотр помечается отклонённым, обходчик открывает экран
разрешения конфликта — и видит расход **простым текстом**:

```dart
for (final line in consumptions)
  Text(ScanConflictStrings.position(line.sparePartName, ...))
```

Кнопок ровно две: «Повторить отправку» и «Удалить». Изменить количество нельзя.
Повтор при неизменившемся складе даст тот же отказ.

Хуже, что «переделать заново» тоже не работает напрямую: задача, по которой есть
осмотр в очереди, **скрыта из списков** (`_scannedTaskUuids` в
`getTasksForMachine`). Отклонённый осмотр остаётся в `scanBox`, значит задача
остаётся невидимой. Единственный путь — удалить осмотр (вместе с фотографиями,
комментарием и фактом закрытия), дождаться, пока задача вернётся в список, и
пройти обход заново.

Для сравнения: у ремонта на этот случай есть `repairClipboardText` — весь ремонт
одним текстом в буфер обмена, чтобы переслать администратору. У осмотра копируется
только список нехватки.

**Что предлагаю.** Дать на экране конфликта тот же редактируемый
`SparePartConsumptionSection`, что и в форме: обходчик правит количества, они
переписываются в `scan.actualConsumptions`, снимается `lastError`, осмотр уходит
снова. `scan.key()` расход не учитывает (это записано в модели явно), поэтому ключ
в боксе не поменяется, и правка безопасна. Работы немного — виджет общий и уже
умеет всё нужное.

## Умеренно

### 4. Сортировка каталога — по кодам символов, а не по русскому алфавиту

**Файлы:** `lib/src/data/data_provider.dart:94`,
`lib/src/data/data_provider_sync.dart:180, 236`

Каталог сортируется `a.name.compareTo(b.name)`. `String.compareTo` в Dart
сравнивает кодовые единицы UTF-16, а не буквы:

* `Ё` — U+0401, `А` — U+0410, поэтому **«Ёмкость» встаёт раньше «Автомата»** и
  вообще раньше всего каталога;
* строчные (`а` — U+0430) идут после всех прописных (`Я` — U+042F), поэтому
  «болт М6» окажется ниже «Ящика», а «Болт М6» — в начале.

В справочнике, где часть номенклатуры заведена с заглавной, а часть нет, лист
выглядит перемешанным, и найти позицию прокруткой нельзя. То же касается окна
выбора позиции в расходе — оно берёт готовый отсортированный список.

**Правка.** Сравнивать по заранее приведённому к нижнему регистру названию (поле
`_nameLower` в `SparePart` уже есть — считается для поиска) и нормализовать
`ё` → `е`. Полноценная локале-зависимая коллация в Dart без дополнительных
пакетов недоступна, но эти два шага закрывают практически все случаи.

### 5. Шаг счётчика жёстко ±1, хотя количества дробные

**Файлы:** `lib/src/repairs/repair_detail_screen.dart:782-786`,
`lib/src/qr/result_controls.dart:192-196`

```dart
void _changeQuantity(int index, double delta) {
  final next = _consumptions[index].quantity + delta;
  if (next < 1) return;
```

Количество на сервере — `Numeric(14, 4)`, то есть литры, килограммы и метры
вполне законны. При этом:

* «−» у позиции с количеством 0,5 даёт −0,5 и **блокируется**: уменьшить дробную
  позицию кнопкой нельзя;
* «Заполнить из нормы» подставит плановые 0,25, а «+» сделает из них 1,25 — шаг
  не соотносится с масштабом величины;
* опуститься ниже 1 нельзя вообще, хотя 0,5 — валидное значение.

Ввод руками это обходит, но кнопки в такой ситуации вводят в заблуждение:
обходчик жмёт «−», ничего не происходит, и причина не объяснена.

**Правка.** Либо шаг от масштаба значения (дробное — 0,1), либо оставить шаг 1, но
нижнюю границу опустить до «больше нуля», а не «не меньше единицы».

### 6. Лист фильтра ЗИП проходит по всему каталогу пять раз на каждое касание

**Файл:** `lib/src/spare_parts/spare_parts_screen.dart:443-453, 470-471, 493-495`

```dart
final warehouses = _warehouseOptions;   // полный проход
final groups = _groupOptions;           // полный проход
final count = _resultCount;             // полный проход
```

Все три — геттеры, считающие по `dataProvider.spareParts` целиком, и все три
вызываются в `build` листа фильтра. Плюс ещё два прохода в `_updateDraft` при
каждой правке. Итого пять проходов по каталогу на каждое нажатие чипа.

Показательно, что сам экран этой ошибки не делает: там результат отбора лежит в
поле `_visible` с явным комментарием, что считать его в `build` нельзя. Лист
фильтра — тот же код, написанный без этой предосторожности.

На стенде 802 позиции, и это незаметно. Каталог заявлен под десятки тысяч; на
50 000 это 250 000 проверок на касание, с заметным подвисанием листа.

**Правка.** Считать варианты и счётчик в поля при изменении черновика фильтра, как
это сделано на самом экране.

### 7. Формат количества пропускает несколько разделителей и любое число знаков

**Файл:** `lib/src/widgets/spare_part_consumption.dart:557-585`

`_QuantityInputFormatter` ограничивает число значащих цифр девятью, но разделитель
пишет в буфер без проверки:

```dart
} else if (char == ',' || char == '.') {
  buffer.write(char);
}
```

Поэтому в поле можно набрать «1.2.3» или «1,,5». `double.tryParse` вернёт `null`,
`onChanged` не вызовется, и на потере фокуса текст молча откатится к прежнему
значению — без объяснения. Так же не ограничено число знаков после запятой:
1,23456 уйдёт на сервер, где `Numeric(14,4)` тихо округлит.

**Правка.** Разрешать один разделитель и не больше четырёх знаков после него —
ровно как `QuantityStepper` в веб-админке, на который формат и ориентирован.

### 8. Отклонённые черновики ремонта не видны на главном экране

**Файлы:** `lib/src/qr/qa_actions.dart:233-245`,
`lib/src/data/data_provider.dart:372-386`

Для отклонённых осмотров сделано правильно: `rejectedScansCount` — это
`ValueNotifier`, и полоса стоит **первой** на главном экране, с явным объяснением
почему («отклонённый осмотр больше никто не отправит сам»).

У черновиков ремонта та же природа отказа — `PendingRepair.isRejected`, причина
записана в `lastError`, автоматически повторять никто не будет, — но на главном
экране про это ничего нет. Плитка «Ремонты» показывает `activeRepairsCount`, и
отклонённый черновик входит в это число наравне с обычным: значок один и тот же.
Узнать об отказе можно, только открыв раздел.

**Правка.** Второй счётчик отклонённых черновиков и такая же полоса — либо общая с
осмотрами, чтобы не заводить на главной два похожих блока.

### 13. `PendingRepairAdapter.read` нарушает собственное правило проекта

**Файл:** `lib/src/model/pending_repair.dart:252-274`

Соседний `SparePartAdapter` читает поля в локальные переменные и объясняет почему:

> Поля читаем по одному, а не прямо в аргументах конструктора: порядок вычисления
> именованных аргументов в Dart совпадает с порядком записи, но полагаться на это
> в формате хранения не стоит.

`PendingRepairAdapter` читает прямо в именованные аргументы — шестнадцать
`reader.read()` подряд внутри вызова конструктора. Сейчас это работает (Dart
гарантирует порядок вычисления слева направо), но при любой перестановке
аргументов формат на устройствах поедет молча.

### 14. Очередь пишет в `print`, а не в логгер

**Файл:** `lib/src/data/data_provider_outbox.dart` — 9 мест

Сообщения об отказах отправки идут через `print`. Все в ветках `catch`, то есть
срабатывают только при ошибке, но именно они нужны при разборе жалобы «расход не
списался». В релизной сборке они уходят в никуда.

## Работает верно

Проверено по коду и сверено с реализацией бэкенда.

| Что | Чем подтверждено |
| --- | --- |
| **Инкрементальная синхронизация каталога ЗИП** | Окно закрепляется между страницами; удаления приходят полным списком на первой странице (`skip != 0` → пусто), клиент собирает их в `Set` — усечения нет; курсор двигается последним, оборванный проход безопасно повторяет то же окно |
| Откат на полный проход | Нет `sync_until` в ответе — клиент не принимает ответ за список изменений и качает каталог целиком |
| Флаг незавершённой записи ЗИП | `markSparePartsWriteStarted` обрамляет `clear()`/`putAll()`, `ensureSparePartsLoaded` его проверяет |
| Полнота полного прохода | Окно «с начала времён» ничего не теряет: на сервере `created_at` — `NOT NULL` с `server_default`, а `coalesce(updated_at, created_at)` всегда определён |
| **Инкрементальная синхронизация ремонтов** | Без фильтра по статусу — намеренно и верно: закрытый ремонт приезжает со своим новым статусом и уходит из кэша активных. Курсор в памяти, полный проход на каждом холодном старте — компенсация того, что передача ремонта другому сотруднику в окно не попадает |
| **Все Hive-адаптеры в области** | `Scan`, `Task`, `SparePart`, `PendingRepair`, `PendingRepairUpdate`, `ConsumptionNorm`: порядок чтения совпадает с записью поле в поле, новые поля только в хвосте под `try/catch`, все 29 `typeId` уникальны, все адаптеры зарегистрированы |
| Расход в ключе осмотра | В `Scan.key()` намеренно не входит, и это верно: ключ обязан быть стабильным у уже поставленных в очередь осмотров. Схлопывания не создаёт — `task_uuid` в ключе уникален |
| Сброс расхода при смене задачи | Сравнивается `uuid` задачи, а не «есть/нет»: переход с одной настроенной задачи на другую тоже обнуляет позиции |
| Задача скрывается, пока осмотр в очереди | `_scannedTaskUuids` с кэшем на одно построение списка; кэш сбрасывается при любой правке очереди — задач-призраков нет |
| Разделение отказов очереди | Истёкший токен, «осмотр уже доставлен», повторяемый сбой и отказ по существу разведены; повторяемое не помечается отказом, доставленное убирается из очереди как при успехе |
| Момент списания | У ремонта склад уменьшает администратор при закрытии (`close_repair`), у осмотра — сервер сразу при `PATCH`. Обе подписи в интерфейсе говорят ровно это |
| `showStockWarnings: !repair.isClosed` | У закрытого ремонта остаток уже уменьшен на этот самый расход, сравнение дало бы ложную тревогу |
| Нормы только ремонтные | `getConsumptionNorms` по умолчанию шлёт `usage_type=repair`, полная синхронизация использует это же значение — нормы ТО в выбор ремонта не попадают |
| Идемпотентность | Черновик уходит с `localId` в `Idempotency-Key`; снимок — с ключом от содержимого кадра, одинаковым для онлайн-попытки и повтора из очереди |
| Защита от зацикливания пагинации | Порог 100 000 записей с записью в лог — во всех циклах, включая инкрементальные |
| Замороженный план осмотра | Бэкенд `28645a6` отдаёт план из снимка; форма ответа не изменилась, мобильной правки не требуется |
