## Серьёзно

### 1. Наработка, застрявшая в pending-боксе, блокирует ТО навсегда

**Файлы:** `lib/main.dart:205-208`,
`lib/src/data/data_provider_outbox.dart:464-506` (`syncUsageScans`),
`lib/src/data/data_provider_outbox.dart:566-577` (шлюз ТО),
`lib/src/data/data_provider_sync.dart:669-677` (`_outboxIsEmpty`)

Очередь наработки, как и очередь осмотров, работает через пару боксов: запись
переносится в pending на время запроса и убирается оттуда в любом исходе.
Разница в том, **что происходит, если исхода не было** — процесс убили, пока
запрос летел.

У осмотров это предусмотрено дважды: на старте приложения pending-бокс
переливается обратно в основной,

```dart
for (var scan in dataProvider.scanPendingBox.values) {
  await dataProvider.scanPendingBox.delete(scan.key());
  await dataProvider.scanBox.put(scan.key(), scan);
}
```

и вдобавок у каждой попытки есть отметка времени (`scan_pending_<key>`), по
которой запись возвращается через 120 секунд.

**У наработки нет ни того, ни другого.** `scanUsagePendingBox` на старте не
трогают, отметок времени у него нет, а `syncUsageScans` перебирает только
`scanUsageBox`. Значит запись, оставшаяся в pending, не будет отправлена
никогда и не попадётся на глаза никому.

Последствий три, и первое — то самое, ради чего вчера чинили находку 1:

1. **Шлюз закрытия ТО ждёт её вечно.** Он проверяет pending-бокс **без**
   фильтра по отказу — там пометке об отказе взяться неоткуда:

   ```dart
   final hasPendingUsage = scanUsageBox.values.any(
         (usage) => usage.equipmentUuid == scan.equipmentUuid &&
             !usage.isRejected,
       ) ||
       scanUsagePendingBox.values.any(
         (usage) => usage.equipmentUuid == scan.equipmentUuid,
       );
   ```

   Осмотр задачи ТО по этому оборудованию не уйдёт, ЗИП не спишется, и на
   экране об этом не будет ни слова: наработка не помечена отклонённой, полоса
   на главной молчит.

2. **`_outboxIsEmpty` навсегда `false`.** Ранний выход цикла отправки перестаёт
   срабатывать, и все пять проходов будят боксы каждые 5 секунд всё время
   работы приложения.

3. **Кнопка «Синхронизировать данные»** по той же причине никогда не отчитается
   «всё отправлено».

Вероятность попасть в это окно невелика — процесс должен умереть ровно во время
`PATCH`, — но Android убивает приложения штатно, а последствие необратимо и
молчаливо. Ровно та жалоба, с которой начиналась находка 1: «закрыл ТО, ЗИП не
списался, ничего не происходит».

**Что предлагаю.** Перелить `scanUsagePendingBox` в `scanUsageBox` на старте
приложения — теми же четырьмя строками, что уже написаны для осмотров, рядом с
ними. Повтор безвреден: если предыдущий запрос всё-таки дошёл, сервер примет
тот же `current_value` повторно.

Если хочется симметрии полной — добавить наработке отметки времени, как у
осмотров. Но для закрытия дыры достаточно перелива на старте: без него запись
не вернётся вообще никогда, с ним — не позже следующего запуска.

## Мелко

### 2. «200 OK без `uuid`» возвращает наработку в очередь без пометки

**Файлы:** `lib/src/http/equipment_api.dart:127-152`,
`lib/src/data/data_provider_outbox.dart:475-482`

`updateUsageParameter` возвращает `false`, когда код ответа успешный, а тело
разобрать не удалось или в нём нет `uuid`. Очередь на `false` кладёт запись
обратно в `scanUsageBox` **без** `lastError`:

```dart
} else {
  await scanUsagePendingBox.delete(scan.key());
  await scanUsageBox.delete(scan.key());
  await scanUsageBox.put(scan.key(), scan);   // назад, неотклонённой
}
```

Повтор пошлёт тот же `PATCH`, сервер ответит так же — и так по кругу, а шлюз ТО
всё это время ждёт. То есть третий вход в тупик находки 1, уже не через
процесс-килл, а через нарушение контракта ответа.

Сценарий редкий: сервер должен вернуть 2xx с телом, где нет `uuid`. Но именно
такие ответы дают шлюзы и прокси.

**Оговорка: часть этой дыры — моя.** Правка находки 9 (разбор тела после
проверки кода) перенесла сюда случай «2xx с массивом или HTML вместо объекта»:
раньше он бросал `TypeError`, очередь относила его к невосстановимым и ставила
пометку. Случай «2xx с объектом без `uuid`» крутился в этом цикле и до неё.

**Что предлагаю.** Не возвращать `false` на успешный код, а бросать исключение
с внятным текстом: очередь отнесёт его к невосстановимым (кода ответа в
сообщении нет — значит не 5xx), поставит пометку, и обходчик увидит наработку
на главной вместо вечного молчания. Три строки в `equipment_api.dart`.

### 3. «Повторить» у наработки не будит очередь

**Файл:** `lib/src/data/data_provider.dart:467-473`

`retryRejectedUsage` снимает пометку и на этом заканчивается, тогда как
`retryRejectedScan` рядом вызывает `syncScans()` сразу:

```dart
Future<void> retryRejectedScan(String key) async {
  ...
  await syncScans();          // ← у осмотра есть
}

Future<void> retryRejectedUsage(String key) async {
  ...
```

Разницы в поведении почти нет — цикл подхватит запись через 5 секунд, — но лист
закрывается сразу, и эти секунды выглядят как «нажал, ничего не произошло».
Стоит добавить `await syncUsageScans();` для симметрии.

## Осознанные решения, которые аудит не считает дефектами

Чтобы их не «чинили» в следующий заход:

* **Расход при двух и более выбранных задачах указать нельзя.** Решение
  заказчика, не техническое ограничение. Сервер принял бы расход по каждой
  задаче отдельным `PATCH` — соблазн есть, и он записан в комментарии.
* **Битый снимок ремонта пропускается, а не срывает отправку.** В `sendScan`
  наоборот, и это не рассогласование: осмотр после успешного ответа исчезает
  из очереди, а очередь ремонта держит путь к файлу до приёма сервером, и
  исключение крутило бы заведомо битый файл вечно. Отличать «повторяемый» от
  «никогда не уедет» очередь снимков пока не умеет.
* **Двойное локальное списание при гибели процесса** между успешным ответом и
  удалением записи из pending: повтор придёт на закрытый осмотр, ветка «уже
  доставлен» уменьшит остаток второй раз. Это заплатка на минуту — ближайшая
  синхронизация перезапишет остаток серверным значением.
* **Курсор ремонтов живёт в памяти**, а не в Hive: окно не сообщает о передаче
  ремонта другому сотруднику, и полный проход на каждом холодном старте
  ограничивает расхождение одним сеансом.
