## Серьёзно

### 1. При отклонении черновика теряется `serverUuid` — ломаются три защиты

**Исправлено.** В `catch` теперь отклоняется накопленный `current`.

В цикле отправки черновиков ремонта серверный uuid записывается в черновик сразу после
создания ремонта, **до** загрузки снимков:

```dart
current = current.copyWith(serverUuid: repair.uuid);
await pendingRepairBox.put(current.localId, current);
```

Но если следующий шаг — загрузка снимков или финальный `updateRepair` — упрётся в отказ
сервера, в бокс записывается **исходный** объект, а не обновлённый:

```dart
await pendingRepairBox.put(
  draft.localId,              // ← draft, а не current
  draft.markRejected(...),    // ← у draft serverUuid == null
);
```

`markRejected` честно переносит `serverUuid` — но переносит его у того объекта, на котором
вызван. У `draft` он `null`, потому что переменная захвачена в начале итерации.

Итог: ремонт на сервере **существует**, а черновик об этом забыл. Три места полагаются на
`serverUuid`, и все три начинают врать.

**а) Удаление черновика спрашивает не то.** `repairs_list_screen.dart:189`:

```dart
final created = (draft.serverUuid ?? '').isNotEmpty;
```

Комментарий рядом объясняет, зачем это нужно: «Удаление в этом случае не отменяет ремонт —
оно бросает его открытым, а оборудование остаётся „В ремонте“. Спрашивать теми же словами,
что и про несозданный ремонт, значит вводить обходчика в заблуждение».

Именно это и происходит. Обходчик видит обычное «черновик не отправлен, удалить?», удаляет —
и оставляет на сервере открытый ремонт с оборудованием, застрявшим в состоянии «В ремонте».
Сам он об этом не узнает.

**б) Счётчик активных ремонтов завышается.** `data_provider.dart:378` не считает черновик
отдельно, если его ремонт уже есть в кэше — сверка идёт по `serverUuid`. Потерян — черновик
и ремонт считаются как два.

**в) Только что созданный ремонт вымывается из кэша.** `data_provider_sync.dart:166`:
фоновая синхронизация оставляет в кэше ремонт, которого ещё нет в ответе сервера, только если
его помнит какой-нибудь черновик — снова по `serverUuid`. Потерян — ремонт удаляется из кэша
до следующей удачной выдачи списка.

Отдельно стоит отметить, что **дубля ремонта не возникает**: повторная отправка идёт с тем же
`Idempotency-Key = localId`, а сервер помнит ключи бессрочно — чистки `repair_idempotency_key`
в бэкенде нет (проверено). То есть последствия — вводящий в заблуждение интерфейс и лишний
запрос, а не задвоенные данные.

**Источник:** `lib/src/data/data_provider_outbox.dart:118`.

## Умеренно

### 2. Тот же дефект в очереди отложенных правок

**Исправлено** симметрично находке 1.

`_syncPendingRepairUpdatesImpl` ведёт себя так же: `current` копится по ходу (снятые с очереди
снимки, выполненные удаления), а при отказе в бокс пишется `update.markRejected(...)` —
исходный объект с полными списками.

Последствия мягче, потому что обе операции самоисцеляются: у отправленного снимка файл уже
удалён с диска, и `_uploadPhotos` его пропустит (`bytes == null`); повторное удаление
отсутствующего на сервере снимка считается успехом. Но работа делается заново, и это
скрывает суть отказа: обходчик видит правку в исходном виде, будто ничего не отправлялось.

**Источник:** `lib/src/data/data_provider_outbox.dart:341`.

### 3. Правила линтера не применяются вообще

**Исправлено.** Подключён `flutter_lints`; проход по вскрывшимся 140 замечаниям
уровня `info` намеренно оставлен отдельной работой.

`analysis_options.yaml` начинается со строки:

```yaml
include: package:analysis_defaults/flutter.yaml
```

Пакета `analysis_defaults` нет ни в `dependencies`, ни в `dev_dependencies` — как и
`flutter_lints`. Включение не разрешается, и это **единственное** предупреждение анализатора:

```
warning - The include file 'package:analysis_defaults/flutter.yaml' … can't be found
1 issue found.
```

То есть проект анализируется с одними встроенными правилами, а секция `linter.rules` в файле
только **отключает** два правила, которые и так никогда не были включены.

Практический смысл: «базовый уровень — 1 предупреждение», на который принято ориентироваться,
держится ровно на этой поломке. Починив включение, вы, скорее всего, увидите сразу много
замечаний — и это будет полезно, но потребует отдельного прохода.

### 4. Каталог ЗИП переписывается через пустое окно

**Исправлено** флагом незавершённой записи: прерванная перезапись читается как
«каталог не синхронизирован», и ленивая загрузка перезаливает его.

`_syncSparePartsImpl` пишет каталог так:

```dart
await sparePartBox.clear();
await sparePartBox.addAll(_spareParts);
```

Экран от этого не страдает — UI читает список в памяти, а он присвоен до очистки. Но между
двумя строками бокс пуст, а каталог — «десятки тысяч позиций»: `addAll` не мгновенный. Если
приложение убьют в этот момент, после перезапуска раздел ЗИП окажется пустым до следующей
синхронизации, и офлайн выбрать позицию расхода будет не из чего.

Соседний метод от этого приёма уже ушёл осознанно — `syncMyRepairs` начинается с комментария
«Без `clear()`: … очистка с последующей заливкой оставляла окно, в котором бокс пуст». Каталог
ЗИП остался на старом варианте.

## Работает верно

Проверено по коду.

| Что | Как сделано |
| --- | --- |
| Идемпотентность создания ремонта | `Idempotency-Key = localId` черновика; повтор возвращает тот же ремонт. Ключи на сервере не протухают — чистки нет, проверено |
| Порядок конвейера | Создание → снимки → финальный PATCH. `serverUuid` пишется в бокс **до** снимков: убьют приложение на середине — второй ремонт не появится |
| Снимки по одному запросу | Сервер принимает список, но при обрыве на середине не узнать, что сохранилось. Один кадр — один запрос, путь вычёркивается сразу |
| Идемпотентность снимка | Ключ считается от содержимого кадра, поэтому совпадает при любом числе повторов и с попыткой из карточки |
| Пропавший файл снимка | `bytes == null` — путь вычёркивается, а не висит в очереди вечно |
| Повторное удаление снимка | Ответ «снимок не найден» считается успехом: цель достигнута |
| Отказ против отсутствия связи | `isRetryableRepairError` разделяет их: нет связи — попытка не засчитывается, сервер отказал — причина пишется по-русски и автоповторы прекращаются |
| Протухший токен | `AuthExpiredException` обрабатывается отдельно: черновик не помечается отклонённым, поднимается флаг и показывается баннер |
| Удаление черновика в полёте | Перед каждой записью в бокс проверяется `containsKey` — удалённый с экрана черновик не воскресает |
| Ключ осмотра в Hive | Расход ЗИП намеренно не входит в ключ: иначе после обновления приложения `delete(scan.key())` не нашёл бы старую запись и осмотр отправлялся бы вечно. Обоснование записано рядом |
| Потерянный ответ по осмотру | `isScanAlreadyDelivered` ловит «Закрытый осмотр нельзя изменить» и убирает осмотр из очереди как при успехе — ровно парная защита к идемпотентности закрытия на бэкенде |
| Задача ТО ждёт наработку | Не уходит, пока по её оборудованию висит непустая очередь наработки: сервер считает следующее ТО от счётчика |
| Снимки до PATCH в очереди правок | PATCH может перевести ремонт в «На рассмотрении», после чего снимки сервер уже не примет |
| Перенос черновика в ремонт | Комментарий **дописывается**, позиции расхода добавляются только новые: количества по совпадающим не складываются, потому что расход — это списание со склада |
| Поиск занявшего ремонта | Выполняется только при отказе именно про занятое оборудование: при промахе он перекачивает весь список, и делать это на каждом отказе значило гонять сеть впустую |
| Пустой каталог ЗИП | У выбора позиции отдельная подсказка вместо общего «ничего не найдено» |
| Защита от параллельного запуска | Есть у `syncPendingRepairs`, `syncPendingRepairUpdates`, `syncScans`, `syncSpareParts` |

## Что осталось за границей проверки

Приложение не запускалось на устройстве — все выводы получены разбором кода, и правки
проверены тем же способом плюс анализатором и тестами. Сценарии, которые стоит проверить
руками: создание ремонта без связи с последующим отказом сервера (находка 1), отправка
осмотра с расходом ЗИП при нехватке на складе, поведение раздела ЗИП после убийства
приложения во время синхронизации каталога (находка 4).

Отдельно стоит знать, почему находка 1 дожила до аудита при зелёных тестах: существующие
тесты проверяют `markRejected` на модели, а модель всегда была верна — неверным был
вызывающий цикл, который передавал ей не тот объект. Циклы очередей в
`data_provider_outbox.dart` тестами не покрыты до сих пор.
