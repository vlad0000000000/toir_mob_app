# Фичи, экраны и потоки

## Навигация

```
/login  (публичный)                       /knowledge_base — публичный, до входа
   └── /actions  — ГЛАВНЫЙ ХАБ
        ├── /qr_scanner → /qr_result → /repair_create → /repairs/:uuid
        ├── /tasks → /details/:index
        ├── /ppr → /details/:index?from=ppr      (если есть ППР с задачами)
        ├── /problems → /qr_result_problems      (если allowRequestsWithoutQr)
        ├── /repairs → /repairs/:uuid | /repair_draft/:localId
        ├── /spare_parts → /spare_parts/:uuid
        └── /notifications → /notifications_settings
```

Настоящий стек: вглубь `push`, назад `backOr(fallback)` — обычный `pop()` с
запасным адресом на случай пустого стека. Системная кнопка «назад» и кнопка в
шапке ведут себя одинаково.

Стек очищают только сбросы: вход, выход, splash, шаги онбординга. После них
корень — `/actions` (или `/login`).

**Анимации переходов нет** — все маршруты отдают `NoTransitionPage`.

Новый маршрут = правка `app_bar.dart`, если заголовок выводится из строки
маршрута. Если заголовок зависит от данных (номер ремонта, название позиции),
экран строит свой `AppBar` — так сделаны карточки ремонта, ЗИП и уведомлений.

## Вход

Логин/пароль → JWT → `GET /v1/user/me`. При сетевом сбое — фолбэк на локально
сохранённых пользователей (**пароль лежит в Hive открытым текстом** — осознанная
плата за офлайн-вход). Роль не `walker` → `WalkerOnlyException`.

**Профиль доступа** (`model/access_profile.dart`, `AccessProfile`). Права роли
доступа, роль, направление, подразделения, `access_version` — из `/v1/user/me`.
Сохраняется JSON-строкой в `stringBox` под `access_profile:<uuid пользователя>`
(не в адаптере `User`), текущий — `DataProvider.accessProfile`
(`ValueNotifier`, ставит сеттер `GlobalState.authUser`). Перечитывается при
входе и в каждом `mainSync` (`syncAccessProfile`). Право проверять только
через `can(code)`: у отключённой роли сервер всё равно отдаёт коды. `null` —
профиль неизвестен (вошли прошлой версией и с тех пор без сети), не «прав нет».

**Закрытый доступ** — общий предок `AccessBlockedException` (наследник
`AuthExpiredException`), два вида:
- `SubscriptionBlockedException` — тариф: сервер пускает на вход, кладя
  `access_state` в ответ, а на рабочие запросы отвечает 403 с `code`
  `subscription_expired` / `company_deactivated`;
- `NoBusinessAccessException` — роль: `access_role_missing`,
  `access_role_inactive`, `company_missing`. `/user/me` при этом отвечает 200,
  причину даёт `AccessProfile.blockCode`.

Поведение у обоих одно:
- На входе: блокировка из ответа входа, из профиля или 403 → отказ с
  причиной (`login/access_blocked_dialog.dart`, «Обратитесь к руководителю»),
  **без офлайн-входа**. Отказ сервера на `/me` (401, 4xx) тоже не уводит в
  офлайн-вход — только обрыв связи и 5xx.
- Офлайн-вход при снятой роли закрыт по сохранённому профилю пользователя
  (`blockCode`) или по отдельной отметке `access_block:<uuid>` в `stringBox` —
  она пишется и тогда, когда профиля нет (сервер без модели доступа, 403 на
  рабочем запросе); снимается следующим удачным онлайн-входом. Вход при сбое
  `/user/me` берёт пользователя из ответа входа, а не из прошлой сессии.
- Офлайн-вход закрыт **по компании** (`data/subscription_blocks.dart`):
  удачный онлайн-вход запоминает компанию логина (`access_scope.company_id`
  из `/me`), блокировка пишется на компанию, а при неизвестной компании —
  на логин; неизвестное считается заблокированным. Онлайн-вход любого
  сотрудника компании снимает её блокировку и запоминает момент
  подтверждения доступа: блокировка логина с неизвестной компанией,
  записанная **раньше** этого момента, для сотрудников этой компании больше
  не действует.
- Во время работы: 403 ловит общий клиент (`_OfflineAwareClient`) и передаёт
  токен и номер сессии **того запроса** (`API.accessSession` запоминается при
  отправке) → `DataProvider.handleAccessBlocked` (туда же —
  `syncAccessProfile`, если профиль пришёл с `blockCode`) реагирует
  только на свою сессию (запоздавший ответ прошлого обходчика — или того же,
  вошедшего заново с совпавшим токеном, — не выкидывает нового), один раз на
  сессию, запоминает блокировку (тариф — в `SubscriptionBlocks`, роль —
  отметкой и `AccessProfile.blockedBy` в профиль) → событие
  `accessBlockEvents` (счётчик, не «залипающее» значение) → `main.dart`:
  выход, переход на `/login`, событие `accessNoticeEvents` и только потом
  ожидание остановки push-сервиса. Экран входа показывает `pendingAccessNotice` по этому
  второму событию (или при открытии) — окно, показанное до перехода,
  переход закрыл бы. Признак обработанной сессии сбрасывается при каждом
  входе (токен того же пользователя в ту же секунду совпадает). Вход после
  начальной синхронизации проверяет, что сессия та же, иначе
  останавливается.
- Очереди не теряют данные: для них это протухший токен — запись остаётся
  без пометки об отказе и уйдёт, когда доступ вернут и обходчик войдёт снова.

Выход не чистит локальные данные.

Известное: `Form` на экране есть, но `GlobalKey<FormState>` нет — `validator`
никогда не вызывается. Фактический паттерн валидации в проекте другой — флаги
подсветки в `State`.

## Разделы и действия по правам роли

Правило одно на все экраны — `SectionAccess` (`data/section_access.dart`,
`DataProvider.sectionAccess`). **Решение продукта: недоступное не прячется**,
а показывается с замком и по нажатию объясняет «Нет доступа … обратитесь к
руководителю» (`showNoAccessDialog`, `widgets/no_access.dart`; тексты —
`AccessStrings`). Профиль неизвестен — не запирается ничего: сервер ответит
сам.

| Где | Нужно |
|---|---|
| Сканер (главная карточка) | найти оборудование (`equipment.view` или `inspection.create` — флаг «Осмотр без QR» не влияет, бэкенд `06b145f`) **и** сделать что-то (`tasks.execute` или `inspection.create`) |
| «Задачи», строка «Задачи» на экране скана | `tasks.execute` |
| «Осмотр оборудования» без QR, строка «Проблема» | `inspection.create` |
| «Ремонты» | `repair.view` |
| «ЗИП», блок расхода ЗИП на экране скана | `spare_parts.view` |
| «Уведомления» | `notifications.view` (запертая — обычная плитка без счётчика) |
| Чип состояния: обычные состояния / «В ремонте» | `equipment.view` **и** (`equipment.change_state` (узкое, только `state`) или `equipment.edit`) — без просмотра сервер отклонит любой PATCH / `repair.create`; нет обоих — чип с замком, есть одно — второе объясняется при выборе |
| Наработка на экране скана | `equipment.view` + `usage_parameters.record` (узкое, только показание) или `usage_parameters.edit`: без права сервер отклонит весь осмотр |
| Ремонт: «Взять в работу», правка, отправка | По `allowed_actions` ремонта (`claim`, `execute`, `submit_review`) — сервер считает их теми же правилами, что и изменения, с областью направления и подразделения (`repairs/repair_access.dart`). Без них (старый сервер, кэш, черновик) — `repair.execute` и ремонт свой; чужой виден по праву «Ремонты всех исполнителей»; плашка объясняет, почему карточку можно только смотреть |
| Ремонт: расход ЗИП | `spare_parts.view`, иначе только просмотр — и `actual_consumptions` не уходит в правку вовсе (`SectionAccess.consumptionsToSend`): сервер с поля, даже пустого, требует право и иначе отклоняет всю правку. Расход уже внесён, а право сняли (`consumptionsBlocked`) — правку не урезают (запись после отправки удаляется, расход пропал бы), а держат с причиной «нет прав»: видна в «Не отправлено», уходит сама, когда доступ вернут |

Главная перерисовывается при смене профиля (подписка на
`DataProvider.accessProfile`); остальные экраны читают права при построении.

## Сканирование и осмотр — ядро продукта

`/qr_scanner` → парсинг JSON из QR, поиск по `uuid` в локальном списке →
`/qr_result`.

Если оборудование не найдено — **молчание**: строки `qrDetectFail*` объявлены,
но не показываются. Известный пробел.

**Экран результата** (`qr_result_screen.dart` + `result_controls.dart`):
паспорт оборудования, выбор задачи, проблема, приоритет, комментарий, фото,
наработка, чип состояния, липкая кнопка «Отправить».

Правила сборки отправляемых `Scan` — в `createScans()`. Взаимоисключение
«задача ↔ проблема» с диалогом разрешения конфликта. Проблема «Другое» требует
и комментарий, и приоритет.

**Внесена только наработка** — всё равно создаётся закрытый осмотр без задачи
и неисправности (`_usageOnlyInspection` в `qr_result_screen.dart`) с
комментарием «Наработка: 1250 м/ч» и снимками, если они есть. Показания
уходят в том же запросе (`usage_updates`), одной транзакцией с осмотром; так
же — вместе с закрытием каждой задачи ТО. Отказ по наработке откатывает осмотр и
разбирается на экране конфликта осмотра. Подробности —
`data-and-integrations.md`.
**Задачу на ТО создаёт сервер по значению наработки, а не по осмотру:**
воркер `check_maintenance_requirements` раз в 10 минут сравнивает
`current_value` с порогом периода у параметров с «создавать задачи на ТО».

**Смена состояния оборудования** происходит немедленно, не по кнопке
«Отправить», и в очередь не ставится. Исключение — «В ремонте», см. ниже.

## Фактический расход ЗИП в осмотре

Закрывая периодическую задачу, обходчик указывает, сколько ЗИП израсходовано.
Блок `spare_part_usage` приходит с **любой** периодической задачей: у настроенной
есть план (`mode` = `norm` или `manual`), у ненастроенной план пуст — списывать
есть что, сравнивать не с чем. У заявки без задачи блока нет.

Расход собирается один раз при отправке и едет в `Scan.actualConsumptions`
готовой строкой JSON — ровно в том виде, в каком его ждёт форма
`actual_consumptions`. Рядом хранится клиентская подпись
`Scan.consumptionNames` (на сервер не уходит) — чтобы через сутки без связи
показать название, а не голый uuid. **В `Scan.key()` расход не входит**: ключ
обязан оставаться прежним у уже поставленной в очередь записи.

**Списывает склад сервер, при приёме осмотра.** Если к моменту отправки позиций
на складе не осталось, он отвечает 409 с `detail_code: insufficient_stock` и
списком `shortages` → `InsufficientStockException`. Очередь помечает осмотр
(`lastError`, `lastShortages`), автоповторов больше нет.

**Экран разрешения конфликта осмотра** — `qr/scan_conflict_screen.dart`,
открывается `Navigator.push` (модальный тупик, как у ремонта). Устроен так:

- всплывает **только на главной** — отказ приходит из фоновой очереди в
  произвольный момент, и экран поверх формы осмотра стёр бы введённое;
- закрытый без решения второй раз сам не всплывает (`_seenConflicts`), но
  полоса на главной остаётся, и по тапу он открывается снова;
- отклонённых может быть несколько — разбираются по одному;
- обходчик правит количества (`Scan.copyWithConsumption` — копия с тем же
  ключом, ложится в бокс на место оригинала) и отправляет заново;
- ничего не удаляется само.

**Отклонённая наработка** разбирается отдельно и проще: не экран, а нижний лист
с выбором «повторить» / «удалить» — правит там нечего, это одно число. Сам он
не всплывает: полоса на главной подождёт.

## ППР

Планово-предупредительный ремонт — набор периодических задач со своим сроком.
Раздел живёт за фича-флагом `FeatureFlags.pprEnabled` (`PPR_ENABLED` в `.env`,
по умолчанию включён); при `false` синхронизация ППР не ходит в сеть и раздел
не показывается даже при наличии кэша.

- **Кнопка «ППР»** на главном хабе появляется, только когда есть ППР в статусе
  `IN_PROGRESS` с доступными обходчику задачами (`hasPprInProgressWithTasks`) —
  кнопка не должна вести на пустой список.
- **`/ppr`** — сворачиваемые блоки по ППР, внутри задачи именно этого ППР.
  Единственный ППР раскрывается сразу. К оборудованию переход
  `go('/details/:id?from=ppr')`, и `MyAppBar` по этому параметру возвращает на
  `/ppr`, а не на `/tasks`.
- **В карточке оборудования** задачи ППР идут отдельной группой «ППР ·
  Название» фиолетового цвета (`kPprGroupName`, `pprGroupColor`), выше групп по
  периодичности.
- **Данные:** `syncPpr()` тянет актуальные ППР (`QUEUED`, `IN_PROGRESS`) и
  детали каждого (N+1 осознанный: активных ППР немного), затем `syncTasks()`
  догружает осмотры задач ППР поштучно — **осмотр задачи ППР актуален, пока ППР
  не закрыт, даже если у него вышел срок**. Отдельного Hive-адаптера у `Ppr`
  нет: снимок кладётся JSON-строкой в `stringBox` (`ppr_active`), прогресс «мои
  выполненные» — в `ppr_completed_by_me`.

## Ремонты

Статусы: «Открыт» → «На рассмотрении» → «Закрыт». Обходчик доводит до
«На рассмотрении»; **закрывает ремонт и списывает склад администратор** в
веб-админке — в приложении такого действия нет.

**Что делает сервер, а не приложение:** сужает список до «моих» (по
ответственному или должности), ставит оборудованию `in_repair` при создании и
возвращает прежнее состояние при закрытии, проверяет уникальность активного
ремонта. Роли `walker` в PATCH разрешены ровно `status`, `comment`,
`actual_consumptions`.

**Длительность** показывать только через `Repair.durationAt(now)`, не поле
`duration`. Сервер (с `ce8525e`) у открытого ремонта считает её до момента
ответа, а в кэш ремонт приходит только при изменении — строка застывала бы.
Поэтому у открытого (кроме черновика, `id == 0`) она считается на телефоне от
`startedAt` функцией `formatRepairDuration` — тот же формат, что
`format_repair_duration` бэкенда («2 дн 16 ч 4 мин»). На рассмотрении и
закрытый — строка сервера. В карточке поле — `_DurationField` с таймером на
рубеж следующей минуты: перестраивается только оно, форма не сбрасывается.

### Два входа

**Из раздела «Ремонты».** Фильтр-чипы статусов (выбор переживает уход с
экрана), черновики из очереди отдельной группой. Закрытые тянутся отдельным
запросом и живут только в памяти экрана.

**Из карточки скана** — чип состояния → «В ремонте». Состояние **не меняется**:
выбор открывает форму создания. Сервер сам ставит `in_repair` при создании и
отклоняет создание для оборудования, которое уже в этом состоянии — поменяй
приложение состояние первым, и ремонт станет невозможно создать. Если ремонт
уже есть, чип показывает «Оборудование в ремонте» с кнопкой «Открыть ремонт»
(работает по локальному кэшу, без сети).

### Карточка

Один виджет обслуживает три режима: серверный ремонт, локальный черновик
(`/repair_draft/:localId`), ремонт с неотправленной правкой (накладывается
поверх серверных данных сразу в `initState`).

Открывается мгновенно: рисует переданный объект или запись из офлайн-кэша, а
запрос к серверу лишь обновляет уже показанное. Закрытые ремонты в Hive не
кэшируются — их передаёт список через `extra`.

Редактируется только в «Открыт». Таблица расхода: плановое количество по норме,
крупный счётчик, подсветка (красный — превышение, зелёный — экономия, жёлтый —
не хватает на складе). У **закрытого** ремонта предупреждений о нехватке нет:
списание уже прошло, остаток уменьшен на этот самый расход.

Свободный ролевой ремонт (должность есть, исполнителя нет) — кнопка «Взять в
работу».

### Разрешение конфликтов

Вид конфликта определяется **один раз, в момент отказа** (`RepairConflictKind`
в `model/repair_conflict.dart`), когда под рукой и текст сервера, и свежая
карточка: постфактум, без связи, экран этого бы уже не смог. Коды хранятся в
Hive строками, а не индексами перечисления.

| Код | Что случилось | Что можно |
|---|---|---|
| `equipment_busy_mine` | Оборудование занял ремонт этого же обходчика | Перенести расход и фото в существующий или удалить черновик |
| `equipment_busy_other` | Занял ремонт другого сотрудника | Переносить нельзя — чужой расход подтверждать не вправе |
| `repair_closed` | Ремонт закрыт администратором | Скопировать данные или удалить |
| `repair_reassigned` | Ремонт передан другому ответственному | Доступа больше нет |
| `other` | Прочий отказ | Отправку можно повторить |

**Данные никогда не удаляются молча.**

## Список оборудования и задачи

`/tasks` и `/problems` — один экран с флагом `isProblems`. В режиме
`isProblems` показывается весь справочник (это выбор объекта для осмотра), в
режиме задач — только оборудование с активными задачами.

**Фильтр «Моё подразделение / Все подразделения»** (режим `isProblems`, решение
продукта). Обходчик с `inspection.create` видит и обслуживает оборудование всей
компании независимо от флага «Осмотр без QR» (бэкенд `06b145f`,
`walker_company_equipment`; контракт — `docs/mobile_access_contract.md` в
бэкенде, статус — `docs/backend-equipment-scope.md` в корне workspace). По
умолчанию «Моё подразделение». Область влияет **только на список**, прав на
запись не задаёт.

**Поиск и фильтры** (макеты `mockups/Мобильное приложение поиск и фильтр задач
и оборудования/`, ТЗ — `docs/search-filters-mobile.md` в корне workspace).
Локально, по кэшу, без сервера. Над списком — `SearchFilterBar`: поиск по
названию, модели и серийному номеру (без регистра и «ё/е», пауза 250 мс) и
кнопка фильтров с числом активных **разделов**. Лист: «Область» (сегменты),
«Местоположение» и «Состояние» (чипы), «Задачи: Все / С активными задачами».
Область и «Задачи» — только в `/problems`: в `/tasks` список и так состоит из
работы обходчика от сервера, прятать её по подразделению нельзя. Порядок
отбора: область → поиск → фильтры, одна функция `applyEquipmentFilter`
(`tasks/equipment_filter.dart`) и для списка, и для «Показать N единиц».
Варианты чипов — из набора выбранной области; при смене области выбранное,
чего там нет, снимается. Фильтр живёт до перезапуска или выхода (свой у каждого режима),
запрос — нет. Пустой результат в «Моё», если во всех подразделениях что-то
есть, — «В других подразделениях найдено N» и кнопка переключения. Карточка
в `/problems` — с подписью «Помещение · Состояние».
При скане QR оборудования не из своих подразделений — всегда окно
предупреждения (`qr/foreign_equipment_dialog.dart`) с «Открыть» и «Отмена»;
открыв, обходчик проводит и отправляет осмотр как обычно. После «Отмена»
сканер молчит 2 секунды, чтобы тот же QR не открыл окно снова.
«Моё» — `isMyEquipment` (`data/equipment_scope.dart`): по подразделению из
справочника (`division.uuid` → `InventoryRecord.divisionUuid`) среди
подразделений роли (`AccessProfile.divisions`); `division: null` — не своё.
Сервер прошлой версии поля не присылает (`divisionUuid == null`) — тогда
по-старому: помещение оборудования среди помещений своих подразделений
(`/v1/company/locations/brief`, `syncMyLocations`, `stringBox`). Без профиля
(старый сервер), при «все подразделения», а по помещению — пока помещения не
загружены и у записи без uuid помещения — считается своим. Оборудование без
помещения — не своё. У оборудования хранятся `locationUuid` и `divisionUuid`
(последние поля Hive-записи; `divisionUuid`: `null` — поля не было, `''` —
`division: null`); записи прошлой версии их не несут — разовая полная сверка
справочника (`equipment_division_uuid_v1`). Открытый экран пересчитывает отбор по `DataProvider.inventoryRevision` (запись справочника, помещений, смена аккаунта) и по профилю доступа.

Кэш рисуется сразу, синхронизация идёт фоном тонкой полоской сверху.

Какие задачи видны — правило `data/task_visibility.dart` (см.
`project-overview.md`, «Пользователь один»). Общую задачу или задачу
направления выполняет любой из группы, закрепляется она за первым, кто
отправит результат; взявшему другим она пропадает из списка. Кнопки «Взять в
работу» у задач нет — решение продукта. Строка задачи подписывается
«Общая задача» или названием чужого направления (`taskScopeLabelFor`); своё
направление не подписывается.

**Возвращённые на доработку** (решения продукта): в общих «Задачах» —
оборудование с ними первым, без отдельной строки «N задач на доработку» (доработка входит в счётчик активных задач — одна задача не считается дважды); на
экране задач оборудования — своя группа «На доработку» выше ППР; строки «причина» под задачей нет — причина и кто вернул в карточке по «i» (`showPeriodicTaskCard(rework:)`, оранжевый блок под заголовком), строкой — только у задачи без карточки. На экране скана при выборе такой задачи над формой блок
`_ReworkCard`: причина, кто вернул, прежний результат (комментарий, расход,
фото) только для чтения и подсказка про расход. Форма пустая; сдаётся только
как выполненная. Подтверждение «ничего не спишется» для неё не показывается —
прежний расход на сервере остаётся. Уведомление — тип
`inspection_returned_for_rework` («Осмотр на доработку»), заголовок и причину
шлёт сервер.

Карточка деталей группирует задачи по периодичности; цвета берутся из
**захардкоженной** `Map<String, Color>` по русскому названию периода. Ключ не
совпал — задача не попадёт ни в одну группу. Хрупко и известно.

На отдельном экране задач оборудования (не в окне выбора задачи при скане
QR) — поиск по названию задачи и узлу и фильтр «Периодичность»: чипы — группы
этого оборудования, все группы ППР одним чипом «ППР», «На доработку» и
«Назначенные задачи» — своими. Остаются только группы с найденным, раскрытые,
счётчик — по найденным. Поиск и фильтр разовые: сбрасываются при уходе с
экрана. Старый фильтр (`TasksFilterState`, статус/приоритет/даты) удалён.

## Уведомления и push

**Контракт: SSE — только сигнал, источник правды REST.** На событие клиент
делает полный `refreshList()`.

Состояние сервиса — шесть `ValueNotifier`. `hasLoadedOnce` существует, чтобы на
холодном старте не мигало «пусто» до ответа сервера — **повторяй этот приём**.

**Отметка прочтения** (`NotificationsService.markRead`) — по тапу в списке и
по тапу на пуш. На экране сразу, без ожидания сервера (`_locallyRead`);
недошедшая из-за связи, таймаута, 401 или 5xx — в `_pendingRead` и досылается
в начале каждого `refreshList()` и после любой дошедшей отметки. Отказ сервера
(404/403) — не повторяется. Очередь дублируется в `stringBox` под логином
(`notifications_pending_read:<login>`): переживает перезапуск, поднимается в
`bootstrap()` того же пользователя. Подгрузка страниц (`loadMore`) тоже
сверяет сессию.
Отметки уходят строго по одной (`_readTail`), `unread_count` сервера
принимается только от последней в очереди — иначе запоздавший ответ
перетирал счётчик. Каждая помнит сессию (`_readSession`, растёт в
`onLogout`): результат запроса, завершившегося после выхода, отбрасывается.
Досылка и каждый круг `refreshList()` держат одну сессию на весь проход и
останавливаются при её смене — иначе следующая отметка из копии очереди
ушла бы с токеном нового пользователя, а ответ списка вернул бы чужой.
Ошибка ловится на каждый круг (`_refreshOnce`), а не на весь цикл: иначе
сбой одного круга терял перечитывание, ждавшее в `_refreshQueued`. Ответ,
устаревший из-за отметки (`_refreshSeq`), отбрасывается с повтором круга —
иначе первая загрузка могла остаться пустой.
Пуш несёт `uuid` уведомления в payload: фоновый изолят передаёт его в
основной (`notification_uuid` в `push_tap`, ключ `push_tap_notification` для
холодного старта), `PushNotificationRouter` отмечает сразу или после входа
(`markPendingRead` из redirect). Раньше тап по пушу не отмечал ничего, а
неудачная отметка из списка терялась молча. Метки холодного старта
(`push_tap_pending`, `push_tap_repair`, `push_tap_notification`) фоновый
изолят пишет **до** сигнала основному, а живой основной, сделав переход,
снимает их — иначе следующий обычный запуск сам прыгал на экран уведомлений
или в старую карточку ремонта.

Выход из аккаунта — только через `login/sign_out.dart` (`signOut()`): он же
сбрасывает уведомления, push-сервис и запомненные фильтры оборудования и ЗИП.
Кнопка «Войти заново» в ремонтах раньше снимала только пользователя.

Push сделан **без FCM**: Android foreground-service держит собственный SSE во
втором изоляте и показывает локальные уведомления. Три пути тапа, все ведут на
`/notifications` (пуш о ремонте — в карточку ремонта). Уведомление сервиса намеренно «тихое»
(`channelImportance: MIN`) — полностью скрыть нельзя, Android API 26+ обязывает.

Надёжность обеих реализаций SSE: реконнект через 5 с, watchdog на 3 минуты
тишины, дедуп по `notification_uuid` в фоновом изоляте. В фоновом изоляте на
**отказ** сервера (ответ не 200: 403 при закрытом тарифе, 401) пауза растёт —
5 с → 30 с → 2 → 5 → 15 мин, сброс по удачному подключению и новому токену:
разлогинить сервис там некому, и после перезагрузки телефона он стучался бы
раз в 5 с. Watchdog, пока реконнект запланирован, паузу не сбивает.

## Пограничные случаи, уже учтённые в коде

| Случай | Как обработан |
|---|---|
| Мигание «пусто» на холодном старте | Флаг `hasLoadedOnce`, спиннер вместо `EmptyState` |
| Двойная отправка осмотра | Один проход очереди (`GenerationPass`), ключ = md5 содержимого, `Idempotency-Key` = `Scan.eventId` на POST и PATCH (409 «обрабатывается» — повтор, 410 — доставлен) |
| Осмотр «только наработка» уходит раньше неё или после её удаления | `Scan.usageKeys` + перенос «положить, потом убрать» + перепроверка записи перед переносом |
| Осмотр завис в pending при убийстве приложения | На старте всё из `pending_scans` возвращается в `scans` |
| Задача ТО уходит раньше наработки | Пропуск отправки, пока есть pending-наработка по тому же оборудованию |
| SSE «тихо умер» | Watchdog 3 минуты → реконнект (в обоих изолятах) |
| Foreground-сервис прибит OEM | Watchdog 90 с + `ensureRunning()` на каждый resume |
| Битая кириллица от сервера | `Utf8Decoder(allowMalformed: true)` на всех GET |
| Ломаный рендер кириллицы на Samsung/Xiaomi | Запрет глобального `tabularFigures` |
| Старые записи Hive без нового поля | `try/catch` вокруг лишнего `reader.read()` |
| Обновление приложения обнуляло базу | Путь Hive без версии + разовый перенос с маркером `.migrated` |
| Повторная отправка ремонта после потери ответа | `Idempotency-Key` = `localId`, сервер вернёт уже созданный |
| Обрыв связи посреди загрузки фото ремонта | По одному файлу на запрос, свой ключ, принятый путь сразу вычёркивается |
| Приложение убито между созданием ремонта и фото | `serverUuid` пишется в черновик **до** фото |
| Оборудование заняли, пока обходчик был офлайн | Черновик помечается отклонённым, экран разрешения конфликта |
| Протух токен во время работы очереди | `AuthExpiredException`, черновик цел, баннер в списке |
| Слеш на конце `API_ENDPOINT` | `API.baseUrl` срезает его на входе — иначе `//v1/...` даёт 404 на всём |
| ЗИП разобрали, пока осмотр лежал в очереди | 409 `insufficient_stock` → пометка на осмотре + экран разрешения конфликта осмотра |
| Общую задачу двое закрыли без связи | Второму 409 `inspection_closed_by_other` → «Задачу уже выполнил и закрыл другой исполнитель», без повтора, только удалить |
| Отказ «взял или закрыл другой», сохранённый прошлой версией | Какой из двух — неизвестно: повтор доступен, сервер ответит точным кодом |
| Задачу взял другой, пока осмотр ждал связи | 409 `already_taken` → «Задачу взял в работу другой исполнитель», повтор доступен — задачу могут вернуть |
| Ремонт ушёл из области, а на нём неотправленная правка | Карточка показывает данные с плашкой «Нет доступа к ремонту», без кнопок отправки и правки — только скопировать или удалить |
| Доступ к ремонту пропал, пока был открыт диалог подтверждения или камера | После ожидания `_stillEditable` перепроверяет: ничего не отправляется и не кладётся в очередь, плашка «Нет доступа к ремонту — изменения не сохранены» |
| Переназначенное ТО (статус `open`) закрыто с новым показанием | Наработка уходит в том же запросе, что и закрытие, — как у плановой задачи |
| ТО закрыто без показания, а более раннее лежит в очереди (наработки или внутри осмотра) | Закрытие ждёт, пока уйдёт показание, — и у планового, и у переназначенного ТО |
| Повторный вход с тем же JWT, а запрос профиля прошлой сессии ещё летит | Номер сессии сдвинулся (`startAccessSession`) — запоздалый ответ выбрасывается |
| Роль лишили права, пока записи ждали связи | 403 `*_denied` → пометка «нет прав», запись хранится; при смене версии доступа уходит заново сама |
| Позицию расхода удалили из каталога | Подпись хранится в самом осмотре (`consumptionNames`), а не ищется в справочнике |
| Сеть есть, сервера нет | `connectionTimeout` 3 с + окно недоступности 30 с: следующие запросы отказывают мгновенно, не ожидая таймаута |
| Прокси ответил 502 вместо сервера | `ServerFailureException.isTransient` — сбой шлюза не считается отказом по существу, черновик уходит в очередь |
| Очередь долбится в мёртвый сервер | Бэкофф цикла отправки 5 → 15 → 60 с + ранний выход, когда все очереди пусты |
| Задача ППР просрочена, но ППР не закрыт | Её осмотр догружается поштучно и не вычищается вместе с закрытыми |

## Что не обработано

- QR не найден — молчание.
- Смена состояния оборудования офлайн теряется (кроме перевода «В ремонте»).
- «Сбросить осмотры» — деструктивно, без подтверждения.
- Валидация формы логина не срабатывает.
- Задача с неизвестным названием периодичности не попадает ни в одну группу.
- Черновик ремонта хранится бессрочно: пока он не уехал, оборудование числится
  в ремонте только на этом устройстве.
