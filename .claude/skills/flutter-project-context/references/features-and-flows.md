# Фичи, экраны и потоки

## Навигация

```
/login  (публичный)                       /knowledge_base — публичный, до входа
   └── /actions  — ГЛАВНЫЙ ХАБ
        ├── /qr_scanner → /qr_result → /repair_create → /repairs/:uuid
        ├── /tasks → /details/:index
        ├── /problems → /qr_result_problems      (если allowRequestsWithoutQr)
        ├── /repairs → /repairs/:uuid | /repair_draft/:localId
        ├── /spare_parts → /spare_parts/:uuid
        └── /notifications → /notifications_settings
```

Настоящий стек: вглубь `push`, назад `backOr(fallback)` — обычный `pop()` с
запасным адресом на случай пустого стека. Системная кнопка «назад» и кнопка в
шапке ведут себя одинаково.

Стек очищают только сбросы: вход, выход, splash, шаги онбординга. После них
корень — `/actions` (или `/login`).

**Анимации переходов нет** — все маршруты отдают `NoTransitionPage`.

Новый маршрут = правка `app_bar.dart`, если заголовок выводится из строки
маршрута. Если заголовок зависит от данных (номер ремонта, название позиции),
экран строит свой `AppBar` — так сделаны карточки ремонта, ЗИП и уведомлений.

## Вход

Логин/пароль → JWT → `GET /v1/user/me`. При сетевом сбое — фолбэк на локально
сохранённых пользователей (**пароль лежит в Hive открытым текстом** — осознанная
плата за офлайн-вход). Роль не `walker` → `WalkerOnlyException`.

Выход не чистит локальные данные.

Известное: `Form` на экране есть, но `GlobalKey<FormState>` нет — `validator`
никогда не вызывается. Фактический паттерн валидации в проекте другой — флаги
подсветки в `State`.

## Онбординг

4 видео + демо-оборудование, машина состояний в `Settings.onboardingStep`.
Демо-uuid `demo-onboarding-conveyor` специально распознаётся в
`DataProvider.getTasksForMachine` и в `QRResultScreen`. **Не сломай демо-ветку**
при правках этих мест.

## Сканирование и осмотр — ядро продукта

`/qr_scanner` → парсинг JSON из QR, поиск по `uuid` в локальном списке →
`/qr_result`.

Если оборудование не найдено — **молчание**: строки `qrDetectFail*` объявлены,
но не показываются. Известный пробел.

**Экран результата** (`qr_result_screen.dart` + `result_controls.dart`):
паспорт оборудования, выбор задачи, проблема, приоритет, комментарий, фото,
наработка, чип состояния, липкая кнопка «Отправить».

Правила сборки отправляемых `Scan` — в `createScans()`. Взаимоисключение
«задача ↔ проблема» с диалогом разрешения конфликта. Проблема «Другое» требует
и комментарий, и приоритет.

**Смена состояния оборудования** происходит немедленно, не по кнопке
«Отправить», и в очередь не ставится. Исключение — «В ремонте», см. ниже.

## Ремонты

Статусы: «Открыт» → «На рассмотрении» → «Закрыт». Обходчик доводит до
«На рассмотрении»; **закрывает ремонт и списывает склад администратор** в
веб-админке — в приложении такого действия нет.

**Что делает сервер, а не приложение:** сужает список до «моих» (по
ответственному или должности), ставит оборудованию `in_repair` при создании и
возвращает прежнее состояние при закрытии, проверяет уникальность активного
ремонта. Роли `walker` в PATCH разрешены ровно `status`, `comment`,
`actual_consumptions`.

### Два входа

**Из раздела «Ремонты».** Фильтр-чипы статусов (выбор переживает уход с
экрана), черновики из очереди отдельной группой. Закрытые тянутся отдельным
запросом и живут только в памяти экрана.

**Из карточки скана** — чип состояния → «В ремонте». Состояние **не меняется**:
выбор открывает форму создания. Сервер сам ставит `in_repair` при создании и
отклоняет создание для оборудования, которое уже в этом состоянии — поменяй
приложение состояние первым, и ремонт станет невозможно создать. Если ремонт
уже есть, чип показывает «Оборудование в ремонте» с кнопкой «Открыть ремонт»
(работает по локальному кэшу, без сети).

### Карточка

Один виджет обслуживает три режима: серверный ремонт, локальный черновик
(`/repair_draft/:localId`), ремонт с неотправленной правкой (накладывается
поверх серверных данных сразу в `initState`).

Открывается мгновенно: рисует переданный объект или запись из офлайн-кэша, а
запрос к серверу лишь обновляет уже показанное. Закрытые ремонты в Hive не
кэшируются — их передаёт список через `extra`.

Редактируется только в «Открыт». Таблица расхода: плановое количество по норме,
крупный счётчик, подсветка (красный — превышение, зелёный — экономия, жёлтый —
не хватает на складе). У **закрытого** ремонта предупреждений о нехватке нет:
списание уже прошло, остаток уменьшен на этот самый расход.

Свободный ролевой ремонт (должность есть, исполнителя нет) — кнопка «Взять в
работу».

### Разрешение конфликтов

Два случая: оборудование занял чужой ремонт (перенести расход и фото в
существующий или удалить черновик) и ремонт уже закрыт администратором
(скопировать данные или удалить). **Данные никогда не удаляются молча.**

## Справочник ЗИП

Поиск, фильтры (склад, группа, наличие), карточка позиции с историей движения.
Только для чтения. Фильтр переживает уход с экрана.

Каталог кэшируется целиком, история движения — нет.

## Список оборудования и задачи

`/tasks` и `/problems` — один экран с флагом `isProblems`. В режиме
`isProblems` показывается весь справочник (это выбор объекта для осмотра), в
режиме задач — только оборудование с активными задачами.

Кэш рисуется сразу, синхронизация идёт фоном тонкой полоской сверху.

Карточка деталей группирует задачи по периодичности; цвета берутся из
**захардкоженной** `Map<String, Color>` по русскому названию периода. Ключ не
совпал — задача не попадёт ни в одну группу. Хрупко и известно.

Фильтр задач написан целиком, но **выключен** константой
`_kShowTasksFilter = false`; фильтр по приоритету в нём всегда отбрасывает всё,
потому что у `Task` нет поля приоритета.

## Уведомления и push

**Контракт: SSE — только сигнал, источник правды REST.** На событие клиент
делает полный `refreshList()`.

Состояние сервиса — шесть `ValueNotifier`. `hasLoadedOnce` существует, чтобы на
холодном старте не мигало «пусто» до ответа сервера — **повторяй этот приём**.

Push сделан **без FCM**: Android foreground-service держит собственный SSE во
втором изоляте и показывает локальные уведомления. Три пути тапа, все ведут на
`/notifications`. Уведомление сервиса намеренно «тихое»
(`channelImportance: MIN`) — полностью скрыть нельзя, Android API 26+ обязывает.

Надёжность обеих реализаций SSE: реконнект через 5 с, watchdog на 3 минуты
тишины, дедуп по `notification_uuid` в фоновом изоляте.

## Пограничные случаи, уже учтённые в коде

| Случай | Как обработан |
|---|---|
| Мигание «пусто» на холодном старте | Флаг `hasLoadedOnce`, спиннер вместо `EmptyState` |
| Двойная отправка осмотра | `_isSyncingScans` + ключ = md5 содержимого |
| Осмотр завис в pending при убийстве приложения | На старте всё из `pending_scans` возвращается в `scans` |
| Задача ТО уходит раньше наработки | Пропуск отправки, пока есть pending-наработка по тому же оборудованию |
| SSE «тихо умер» | Watchdog 3 минуты → реконнект (в обоих изолятах) |
| Foreground-сервис прибит OEM | Watchdog 90 с + `ensureRunning()` на каждый resume |
| Битая кириллица от сервера | `Utf8Decoder(allowMalformed: true)` на всех GET |
| Ломаный рендер кириллицы на Samsung/Xiaomi | Запрет глобального `tabularFigures` |
| Старые записи Hive без нового поля | `try/catch` вокруг лишнего `reader.read()` |
| Обновление приложения обнуляло базу | Путь Hive без версии + разовый перенос с маркером `.migrated` |
| Повторная отправка ремонта после потери ответа | `Idempotency-Key` = `localId`, сервер вернёт уже созданный |
| Обрыв связи посреди загрузки фото ремонта | По одному файлу на запрос, свой ключ, принятый путь сразу вычёркивается |
| Приложение убито между созданием ремонта и фото | `serverUuid` пишется в черновик **до** фото |
| Оборудование заняли, пока обходчик был офлайн | Черновик помечается отклонённым, экран разрешения конфликта |
| Протух токен во время работы очереди | `AuthExpiredException`, черновик цел, баннер в списке |
| Слеш на конце `API_ENDPOINT` | `API.baseUrl` срезает его на входе — иначе `//v1/...` даёт 404 на всём |

## Что не обработано

- QR не найден — молчание.
- Смена состояния оборудования офлайн теряется (кроме перевода «В ремонте»).
- «Сбросить осмотры» — деструктивно, без подтверждения.
- Валидация формы логина не срабатывает.
- Задача с неизвестным названием периодичности не попадает ни в одну группу.
- Черновик ремонта хранится бессрочно: пока он не уехал, оборудование числится
  в ремонте только на этом устройстве.
