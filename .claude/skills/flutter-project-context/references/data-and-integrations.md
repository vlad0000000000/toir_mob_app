# Данные и интеграции

## Бэкенд

Единственный внешний API — **Sampo Smart** (FastAPI, репозиторий
`sampo_smart_backend` в том же workspace). Базовый URL из `.env`
(`API_ENDPOINT`), читается один раз при старте — смена адреса требует
перезапуска.

`API.baseUrl` **срезает завершающие слеши** на входе. Это не косметика: все
методы клеят путь как `'$baseUrl/v1/...'`, и слеш в конфиге давал
`https://host//v1/...`, на что бэкенд отвечает 404 — отваливалось всё, включая
`isAlive()`, и приложение показывало «нет соединения» при живом сервере.

HTTP-клиент — **`package:http`**. `dio` в зависимостях есть, не используется.

### Организация

```
http/api.dart          ядро: baseUrl, jwtToken, таймауты, _client, окно
                       недоступности, _guardOffline, isAlive, разбор detail
  part auth_api        part equipment_api    part task_api
  part scan_api        part notifications_api
  part repair_api      part spare_part_api   part ppr_api
```

`API` фактически stateless — всё состояние в статиках, инстансы создаются
свободно: `API()`.

### **[ЖЁСТКО]** Общий клиент и окно недоступности

Все запросы приложения идут через **`_client`** — `_OfflineAwareClient` поверх
`IOClient` с `connectionTimeout` 3 с. Top-level `http.get/post` в методах API не
место: они поднимают собственный клиент мимо этого таймаута и, главное, мимо
отметки о недоступности. Пять таких вызовов уже пережили переход на общий
клиент и вели себя заметно — успешный запрос мимо обёртки не снимал отметку.

Как устроена отметка (`api.dart`):

- запрос не доехал (`isOfflineError`) → `API.markServerUnreachable()`, сеть
  закрыта на `API.offlineWindow` = **30 секунд**;
- пока окно стоит, `_client` мгновенно бросает `SocketException` того же вида,
  что при реальном обрыве — очередь и экраны уже умеют его разбирать;
- любой ответ сервера снимает окно (`markServerReachable`);
- пинг живости идёт через отдельный **`_probeClient`** и окно игнорирует —
  иначе выйти из него было бы нечем;
- явное действие обходчика (вход, «Синхронизировать данные», «Повторить»)
  вызывает `API.retryConnectionNow()`: отвечать «связи нет» по памяти
  полуминутной давности нельзя.

Таймауты: `_readTimeout` **8 с** (GET, мелкие записи, login), `_uploadTimeout`
60 с (multipart), `_aliveTimeout` 5 с (`isAlive`).

**Публичные пути менять нельзя** без согласования с бэкендом.

**Пагинация:** параметр URL `skip`, аргумент метода `offset`. Цикл выходит на
неполной странице (`length < limit`), а не на пустой — иначе каждый справочник
делал бы лишний round-trip. Предохранитель `_guardPagingLimit` (100 000
записей) обрывает проход **ошибкой**: неполная выгрузка не пишется, граница
окна не двигается. Инкрементальные справочники (оборудование, неисправности,
ЗИП) запрашивают окно с отступом `DataProvider.syncOverlap` = 5 минут назад от
границы — ловит долгие транзакции сервера.

**Оборудование и неисправности — курсором** (`pagination=cursor`,
подписанный `next_cursor`; `loadSyncWindow` в `data/sync_window.dart`). По
`skip` удаление записи между страницами сдвигало смещение, и следующая
пропускалась до полной сверки. Конец окна — **только** `next_cursor == null`
(пустые `items` — не конец: идут удаления, у них свой счёт страниц).
Продолжение — только `cursor`, окно зашито в него. 422 на курсоре
(`SyncCursorRejected`) — окно заново, один раз. В ответе нет `next_cursor`
(старый сервер) — откат на `skip`. Окно пишется только выбранным целиком.
ЗИП, ремонты и остальные — пока по `skip` (у ЗИП на сервере курсора нет).

**Фильтруй на сервере.** Открытые задачи качались по всей компании и
отбирались на телефоне, пока не начали передавать `responsible_user_uuids`.
Открытые качаются **двумя** запросами — по ответственному и по исполнителю
(`inspector_uuids`) — и сливаются по uuid (`loadAllOpenTasks`): `reassign` на
сервере ставит `inspector` и переводит задачу в `open`, не трогая
ответственного, и переназначенная задача иначе не приходила. Видна, если я
ответственный или исполнитель и есть право действия (`isOpenTaskAvailable`).
Исполнитель — назначение **только у экземпляра задачи**
(`TaskAccess.isTaskInstance`, у него есть `direction_scope`): у прямого
осмотра сервер пишет в `inspector` автора, и заявка, заведённая обходчиком и
назначенная другому, попала бы в его задачи. Отфильтровать это в запросе
нельзя — страница короче `limit` оборвала бы постраничную загрузку.
Плановые (`status=scheduled`) идут с `only_my_roles=true&executable_only=true`:
сервер отдаёт общие задачи, задачи направления обходчика и взятые им, а
взятые **другим** исполнителем отсекает сам. Сервер прошлой версии
`executable_only` не знает — для него клиент по-прежнему отсекает их по
`allowed_actions` (`data/task_visibility.dart`). Часть записей страницы
клиент отбрасывает ещё и по окну времени, поэтому конец постраничной
загрузки — по числу пришедших записей (`getCurrentTasks().fetched`), а не
отобранных. Задачи ППР догружаются
поштучно (`GET /fault_inspections/{uuid}`) мимо этого фильтра, поэтому
клиент повторяет его сам — `isTaskInMyScope`.

**Доступ к экземпляру задачи** — `TaskAccess` (`model/task_access.dart`):
`inspector`, `direction_scope` (`single` / `all` — общая / `legacy_multiple`),
`directions`, `allowed_actions` из ответа осмотра. Считается по сохранённому
контексту **экземпляра**: `periodic_task.custom_roles` у общей задачи пустой и
для видимости не годится. Хранится JSON-строкой последним полем `Task`.
Разбирается через `TaskAccess.fromServer`: нет ключа `allowed_actions` (старый
бэкенд без модели доступа) — `null`, «неизвестно», и задачи видны по-старому;
явный пустой список — сервер действительно запретил.

**Возврат на доработку** (бэкенд `ec92144`). Проверяющий возвращает уже
сданный результат исполнителю (`POST /fault_inspections/{uuid}/return`); статус
осмотра остаётся `closed`, признак — блок `review` (`state: returned`,
`return_comment`, `returned_by`, `revision`). Разбирается в `TaskAccess`
(`returned`, `returnComment`, `returnedBy`, `reviewRevision`) — та же
JSON-строка, без правки Hive. `Task.isReturnedForRework` — статус `closed` и
признак вместе.
- Загрузка — третьим проходом `syncTasks`:
  `GET /fault_inspections/?status=closed&executable_only=true`
  (`loadReturnedTasks` → `getReturnedTasks`). Только у сервера, который возврат
  умеет (`DataProvider.returnsSupported`): признак — блок `company` в
  `/user/me`, он из той же версии бэкенда. Сервер прошлой версии параметр
  пропустит и отдаст все закрытые осмотры — поэтому без признака не ходим, а
  страница не из возвращённых выключает запрос до перезапуска. Признак ещё
  неизвестен (первый проход после запуска, профиль грузится параллельно) —
  `loadReturnedTasks` отдаёт `null`, и доработки берутся из кэша, а не
  стираются.
- Видимость — `isReturnedTaskAvailable`: исполнитель — я, есть `execute`.
- Повторная сдача — обычный осмотр закрытия с `Scan.reviewRevision` (поле формы
  `review_revision`, последнее поле адаптера). Устаревшая версия (вернули ещё
  раз, пока осмотр ждал связи) — 409 без машинного кода, текст с именем поля
  переводится в `ScanQueueStrings.errorReworkOutdated`. Расход: не передан —
  на сервере прежний, передан — заменяет, сервер спишет или вернёт разницу;
  поэтому у доработки локальные остатки не уменьшаются (`Scan.isRework`).
- Отметка «закрыто на телефоне» (`closed_task_*`) хранит версию результата
  (`rev:N`, `closedMarkValue`); вернули позже — версия у сервера выросла, и
  отметка задачу не прячет (`isClosedMarkCurrent`). Отметки прошлой версии
  (`'1'`) — версия `-1`, возвращённую задачу не прячут.

### Заголовки, кодировка, multipart

Состав задач у ППР отдаёт только детальный ответ, поэтому `getActivePprs()`
делает N+1 запрос — осознанно: активных ППР немного. Отказ на любых деталях
обрывает **всю** синхронизацию ППР: пропустить один — значит убрать его задачи
из списков до следующего удачного прохода, а сохранённый снимок остался бы цел.

- `Authorization: Bearer {jwt}` — везде, кроме `login` и `isAlive`.
- Каждый GET декодируется вручную через `Utf8Decoder(allowMalformed: true)` —
  защита от битой кириллицы. Не заменяй на `response.body`.
- Multipart: `sendScan`, `updateEquipmentState`, фото периодической задачи,
  `uploadRepairPhotos`. Фото передаются base64-строками и декодируются перед
  отправкой; битый кадр логируется и пропускается, отправка не срывается.
- **Снимки ремонта в очереди — файлы на диске** (`data/repair_photo_files.dart`),
  а не base64 в Hive: черновик может ждать связи сутками. Уходят **по одному
  запросу на кадр** — сервер принимает список, но при обрыве на середине узнать,
  что сохранилось, было бы неоткуда.

### Что сервер делает за клиента (ремонты)

1. Сужает выдачу `/v1/repairs/` до ремонтов пользователя и его должности.
2. Ставит оборудованию `in_repair` при создании ремонта и возвращает прежнее
   состояние при закрытии.
3. Белый список полей PATCH для роли `walker`: `status`, `comment`,
   `actual_consumptions`. Лишнее поле → 403. Исключение — захват свободного
   ролевого ремонта одиночным `responsible_user_uuid`.

### Что сервер делает за клиента (расход ЗИП по осмотру)

`PATCH /v1/company/fault_inspections/{uuid}` принимает поле формы
`actual_consumptions` и **сам списывает склад** при приёме осмотра. Не хватило
остатка — 409 с машиночитаемым телом: `code: "insufficient_stock"` (бэкенд
`ec92144`; прежнее имя поля `detail_code` сервер шлёт рядом на переходный
период, клиент читает оба — `code` первым) и `shortages` вида `{spare_part_uuid, spare_part_name, required, available}`.
Клиент разбирает его в `InsufficientStockException` и хранит вместе с осмотром
(`Scan.lastShortages`), потому что экран разрешения конфликта открывается и
через сутки без связи.

Расход можно указать и по задаче, для которой норму в админке не выбирали: оба
прежних запрета (блок `spare_part_usage` только у настроенных задач и отказ
PATCH по остальным) сняты.

### Идемпотентность

`createRepair` и `uploadRepairPhotos` принимают `Idempotency-Key`; сервер помнит
пару «компания + ключ» и на повтор возвращает уже созданную сущность с кодом
200. На этом держится офлайн-очередь ремонтов. Пустую строку сервер считает
ошибкой — заголовок ставится только при непустом ключе.

Осмотр — и создание (POST), и закрытие задачи (PATCH
`/v1/company/fault_inspections/{uuid}`) — шлёт `Idempotency-Key` =
`Scan.eventId`, постоянный идентификатор события, считается один раз при
создании (`Scan.newEventId`). **Не `Scan.key()`**: тот без времени, два разных
осмотра с одинаковым содержимым дали бы один ключ. Записи прошлых версий без
`eventId` уходят без заголовка. Сервер (с `ec6270e`, миграция `m2026101801`)
на повтор отвечает 200 прежним результатом; после отказа с откатом тот же ключ
можно слать с исправленной формой (повтор с исправленным расходом ЗИП). Ответы
по ключу (`scan_error_messages.dart`): 409 «Idempotency-Key is being
processed» — повторить; 410 «…no longer exists» — доставлено (осмотр удалили
на сервере); 409 «…with a different request» — отказ.

**Наработка в составе осмотра** — поле формы `usage_updates`, строка JSON
`[{"usage_parameter_uuid", "current_value": "1250.00"}]` (`Scan.usageUpdates`,
собирает `usageUpdatesPayload`). Сервер применяет её в одной транзакции с
осмотром: отказ по наработке откатывает и осмотр. Значение — строкой с двумя
знаками (`Numeric(15, 2)`; лишний знак — 422 всего осмотра), ввод
ограничен в `UsageParameter.validate`. Уходит так у осмотра «только
наработка» и у закрытия **каждой задачи ТО** в пачке — плановой и открытой
(переназначенное ТО приходит со статусом `open`, а сервер пересчитывает
следующее ТО по задаче самого осмотра; отдельной очередью показание ушло бы
позже закрытия). У открытого ТО, как у планового, в осмотре хранится
`periodicTaskUuid`: по нему `addScan` ставит признак `maintenance_task_*`, и
закрытие без нового показания ждёт показание, уже лежащее в очереди
наработки или — более раннее по времени — внутри другого осмотра в очереди
осмотров (`isUsageOrderBlocked`) (иначе ТО, ушедшее без
показания после сбоя первого, посчиталось бы от старого счётчика; повтор того
же значения сервер принимает); в остальных случаях
наработка — отдельной очередью (`PATCH .../usage-parameters/{uuid}`), чтобы
отказ заявки или нехватка ЗИП не держали показание. **Мобилку с этим
выпускать только вместе с бэкендом**: старый сервер поле молча проигнорирует,
и наработка потеряется.

## Аутентификация

JWT Bearer. `POST /v1/auth/login` → `GET /v1/user/me`. `User` кладётся в бокс
`users` под ключом `username` и отдельно под `auth_user` — это и есть текущий
пользователь. `API.jwtToken` — геттер по `GlobalState.authUser`.

**Refresh-токенов нет.** Есть частичная обработка 401: `_throwServerError`
выделяет его в `AuthExpiredException`, и очередь ремонтов отличает «сервер
отказал» от «протух токен» — черновик не помечается отклонённым, поднимается
флаг `DataProvider.authExpired`, список показывает баннер. Флаг очереди
меняют только через `SessionGuardedFlag`: номер сессии запоминается до
запроса, и 401/403 на запрос, ушедший до выхода, после нового входа
«Сессия истекла» не поднимает. Успешная отправка ремонта, правки, осмотра
или наработки текущей сессии флаг снимает. Автоматического
выхода на `/login` нет. Остальные методы превращают 401 в обычный `Exception`,
который `sync*` проглотит.

**403 с `code`, закрывающим доступ целиком** — `subscription_expired`,
`company_deactivated` (тариф), `access_role_missing`, `access_role_inactive`,
`company_missing` (роль) — общий клиент превращает в `AccessBlockedException`
на **любом** запросе и выводит обходчика на экран входа — см. «Вход» в
`features-and-flows.md`. 403 «нет прав на это действие»
(`permission_denied`, `direction_denied`, `division_denied`) сюда не
относится: он идёт обычным отказом. Выход — `login/sign_out.dart`
(`signOut`), один для кнопки «Выйти» и принудительного выхода.

**Модель доступа сервера** (`feat/roles`). Тип учётной записи (`role` в
ответе входа, `walker`) только пускает в приложение; что можно делать, задаёт
роль доступа: набор прав из каталога бэкенда (`backend/security/permissions.py`;
нужные приложению — `Perm` в `model/access_profile.dart`), одно направление
или ни одного, плюс подразделения пользователя. Чтение сервер режет сам:
без права на раздел мобильные списки отвечают 200 с пустым результатом, а не
403. Права приложение получает из `/v1/user/me` (`AccessProfile`, см. «Вход» в
`features-and-flows.md`). `custom_role_id` и `effective_role` в `/user/me` —
поля совместимости, бывают `null`: каноничные — `direction`, `permissions`,
`divisions`, `access_version`.

**Офлайн-вход** сравнивает пароль с локально сохранённым — **пароль лежит в
Hive открытым текстом**. Осознанный компромисс, шифрования Hive нет.

Тип `walker` — единственный допуск. Видимость задач — по `TaskAccess` и
профилю доступа; `customRoleId` остался запасным правилом для задач в кэше
прошлой версии (без `TaskAccess`). Наработка — все параметры оборудования
при праве ввода показаний; без права `usage_updates` в осмотр не попадают
(`createUsageScans`), иначе сервер откатил бы весь осмотр. Разделы
и действия по правам запирает `SectionAccess` (см. `features-and-flows.md`,
«Разделы и действия по правам роли»).

## Локальное хранилище — Hive

### Расположение

`HiveStorageLocation.resolve(packageInfo)` (`data/hive_storage_location.dart`),
вызов в `main.dart`. Имя каталога — md5 от `appName|packageName`, **без версии**,

## Синхронизация

**Модель: сервер перезаписывает справочники, клиент владеет очередью.**

| Направление | Стратегия |
|---|---|
| Каталог ЗИП, оборудование, типовые неисправности | Инкрементально: окно `updated_since` + список удалённых. Полная перезапись — на первом проходе, после сбоя записи и (оборудование, неисправности) раз в `DataProvider.fullResyncInterval` = 3 суток. Входят в `mainSync`. См. ниже |
| Активные ремонты | Инкрементально, курсор **в памяти**: полный проход на каждом холодном старте |
| ППР | Список актуальных + детали каждого; снимок JSON-строкой в `stringBox`, осмотры задач ППР догружаются поштучно |
| Остальные справочники | Полная перезапись: `box.clear()` + `addAll()`. ETag нет нигде |
| Любая запись по ответу сервера | Только через очередь фиксации с проверкой поколения кэша — см. «Смена аккаунта» ниже |
| Осмотры, наработки, ad-hoc задачи | Очередь в Hive с ретраями до успеха |
| Черновики и правки ремонтов | Очередь с `Idempotency-Key` вместо таймаута возврата |
| Активные ремонты | Кэшируются — карточку можно открыть и править без сети |
| Закрытые ремонты, история движения ЗИП, уведомления | **Не кэшируются** |
| Состояние оборудования | Отправляется сразу, в очередь не ставится. Исключение — «В ремонте»: идёт через создание ремонта и потому переживает офлайн |

### `mainSync()`, ППР и каталог ЗИП

`mainSync()` тянет десять справочников **параллельно** (`Future.wait`), каждый
глотает свою ошибку. Триггеры: фоновый цикл раз в 60 с, вход в «Задачи», «ППР»,
«Сканер», «Осмотр оборудования», после отправки осмотра, после логина.

**Пара «ППР → задачи» — единственная последовательная:** `syncTasks()` по
составу ППР догружает его осмотры и пишет всё в бокс задач одной операцией,
поэтому `syncPpr()` обязан завершиться раньше. Внутри `Future.wait` они идут как
`syncPpr().then((_) => syncTasks())` — параллельно со всем остальным.

**Пока стоит отметка недоступности, `mainSync` не начинается вовсе**
(`API.isServerKnownUnreachable`): десять параллельных проходов, часть из них
постраничные, и каждая страница ждала своего таймаута.

**Каталог ЗИП снова внутри `mainSync`** — после перевода на инкрементальный
проход это один запрос с пустым ответом. Его исключали, когда каждый проход
перекачивал десятки тысяч позиций сотнями страниц, но за это остатки на складе
отставали: обновлялись раз в десять минут или вручную, и в расходе по ремонту
обходчик видел вчерашние числа. Полным проход бывает только на первом заходе и
после оборванной записи — худший случай остался прежним, но разовым.

`ensureSparePartsLoaded()` остался для экранов, которым каталог нужен сразу
(раздел ЗИП, список и карточка ремонта, экран конфликта осмотра): грузит,
только если кэш пуст, экран не ждёт. Кнопка «Синхронизировать данные» тянет
каталог всегда.

От параллельного запуска защищены `mainSync`, `syncSpareParts` и ручная
`syncDataAndScans`: второй вызов присоединяется к идущему проходу — но только
того же поколения кэша (того же аккаунта). Правило одно на всех —
`GenerationPass<T>` (`data/generation_pass.dart`), своих копий не заводить.
У ручной синхронизации он же ведёт флаг `manualSyncRunning` (крутящаяся иконка
на главной); `clearCachedData` забывает её проход (`forget`) и гасит флаг, чтобы
новый обходчик не ждал окончания чужой синхронизации. Отдельные `sync*`,
вызванные мимо `mainSync`, защиты от наложения не имеют; их записи всё равно
сериализует очередь фиксации.

#### Смена аккаунта: поколение кэша и очередь фиксации **[ЖЁСТКО]**

При входе другого обходчика `ensureAccountScope` → `clearCachedData` выбрасывает
кэш. Синхронизация к этому моменту может быть в полёте, и её ответы — данные
прошлого аккаунта. Защита — `CacheCommitQueue` (`data/cache_commit_queue.dart`):

- `clearCachedData` сразу увеличивает поколение (`invalidate`), а саму очистку
  ставит в ту же очередь, что и записи;
- каждый, кто пишет данные аккаунта по ответу сервера, запоминает
  `cacheGeneration` **до** запроса и пишет **только** через
  `_commit(generation, 'что', () async {...})`. Поколение сверяется внутри
  очереди, непосредственно перед записью; устаревший проход отбрасывается
  целиком;
- внутрь фиксации — всё, что составляет результат: боксы, данные в памяти,
  курсор, служебные отметки. Проверка «перед записью» снаружи не годится:
  между `clear`, `putAll` и курсором смена аккаунта вклинивалась, и старый
  проход затирал уже загруженные данные нового;
- **внутри фиксации — никакой сети и никаких вложенных `_commit` /
  `clearCachedData`**: очередь общая, вложенный вызов её повесит;
- экраны, кладущие ответ сервера в кэш (`upsertRepair`,
  `cacheConsumptionNorms`), передают поколение, взятое до запроса. Очередь
  отправки зовёт `upsertRepair` без него — пишет сразу (очередь к аккаунту
  не привязана, это отдельный открытый вопрос).

#### Инкрементальные справочники

Каталог ЗИП, оборудование и типовые неисправности. Сервер принимает
`updated_since` и `sync_until` (оба UTC) и отвечает не списком, а объектом:

```json
{ "items": [...], "deleted": [{"uuid": "...", "deleted_at": "..."}], "sync_until": "..." }
```

Разбор ответа — `parseSyncPage` / `SyncPage<T>` (`http/sync_page.dart`); у ЗИП
исторически своя `SparePartsPage`. Как это устроено на клиенте
(`data_provider_sync.dart`):

- **Курсор** — в `stringBox` (`spare_parts_cursor`, `equipment_cursor`,
  `typical_problems_cursor`), серверный `sync_until` прошлого прохода. У ЗИП
  отдельно есть `spare_parts_sync_at` — локальное время для подписи «Остатки
  на …». В окно запроса местное «сейчас» подставлять нельзя, часы телефона и
  сервера расходятся.
- **Полный проход** — когда курсора нет, бокс пуст, прошлая запись оборвалась
  (флаг `*_write_in_progress`) или, у оборудования и неисправностей, подошла
  редкая сверка (`isFullResyncDue` в `data/sync_schedule.dart`, отметка
  `*_full_sync_at`): дельта не исправляет расхождений, которые сервер не
  сообщил в `deleted`.
  Идёт как окно «с 1970 года»: тем же запросом приходит `sync_until`, иначе
  курсор было бы неоткуда взять. Он же переводит бокс на **ключи по uuid** —
  раньше ключи были автоинкрементными, и точечное обновление было невозможно.
- **Инкрементальный проход** — окно от курсора; `sync_until` первой страницы
  закрепляется и передаётся в остальные, иначе позиция, изменившаяся между
  запросами, съехала бы на уже прочитанную страницу.
- **Удаления** — из `deleted`: сервер ведёт таблицу «надгробий» и туда же кладёт
  заархивированные интеграцией. Без этого списка удалённая позиция осталась бы
  в хранилище навсегда.
- **Откат** — если `sync_until` в ответе нет (сервер режим не понимает), клиент
  возвращается к полному проходу.
- **Смена доступа** — курсор, выданный до смены роли, прав или области
  обходчика, сервер не принимает: отвечает пустым окном с
  `resync_required: true` (`SyncPage` / `SparePartsPage` / `RepairsPage`
  `.resyncRequired`). Клиент идёт на полный проход: то, что ушло из области,
  сервер удалением не пришлёт. У каталога ЗИП своя отметка смены доступа на
  сервере — меняется только при смене доступа к ЗИП.
  Признак проверяется на **каждой** странице: курсор полного прохода тоже
  привязан к версии доступа, и посреди прохода продолжение приходит пустым с
  `next_cursor: null` — без проверки это выглядело бы концом окна и легла бы
  половина. Бросается `SyncAccessChanged`: `loadSyncWindow` начинает окно
  заново (один раз), полные проходы ЗИП и ремонтов ничего не записывают.
- **Курсор двигается последним**: оборванный проход повторит то же окно, а повтор
  безвреден — записи кладутся по ключу, удаление уже удалённого ничего не делает.
- **Порядок на диске больше не отсортирован**, поэтому каталог сортируется в
  памяти: в конструкторе `DataProvider` на старте и после каждого прохода.

- **Путь со слешем на конце** (`/v1/company/equipment/`, `/eq_fault/`): без
  него FastAPI отвечает 307, и каждая страница уходила дважды.

Осмотры, нормы и ППР `updated_since` на сервере тоже принимают, но клиент их
пока качает целиком.

### Очереди отправки

Цикл отправляет осмотры, наработки, ad-hoc задачи, черновики ремонтов и
отложенные правки. Просыпается через **5 → 15 → 60 секунд**: пока сервер помечен
недоступным, шаг растёт (`_outboxBackoffSeconds`) — без бэкоффа цикл долбился в
мёртвый сервер каждые пять секунд весь день. Перед проходом три отсечки: окно
недоступности, `GlobalState.isAuthorized` (иначе `Exception('Not authenticated')`
принимался бы за отказ по существу и осмотр помечался отклонённым) и
`_outboxIsEmpty` — очереди почти всегда пусты.

**Схема А — без побочного эффекта** (осмотры, наработки, задачи):
запись перекладывается в `pending_`, при неуспехе возвращается через **120
секунд** (комментарии в коде местами говорят «60» — верь коду).

Тонкости: каждая очередь (`syncScans`, `syncUsageScans`, `syncPeriodicTasks`)
идёт одним проходом — повторный вызов присоединяется к идущему через
`GenerationPass` (а не возвращается сразу: ручной синхронизации нужен
результат). **Кто только что сделал запись готовой к отправке** (ручная
синхронизация, повтор отклонённого осмотра) зовёт `syncScansFresh` /
`syncUsageScansFresh` — `GenerationPass.runFresh`: дождаться идущего прохода и
запустить свой. Идущий снял снимок раньше и такую запись уже пропустил; задача ТО не уходит, пока по её оборудованию висит непустая
очередь наработки (сервер пересчитывает следующее ТО от счётчика); на старте
`pending_scans` целиком возвращается в `scans`.

**[ЖЁСТКО] Переходы между боксами.** Проход берёт снимок списка в начале и
долго по нему идёт, поэтому перед переносом каждой записи заново проверяет,
что она ещё в боксе (её могли удалить: «Удалить», «Сбросить осмотры»).
И наработку, и осмотры переносят «сначала положить, потом убрать»
(`_moveScan`, `_returnUsageToQueue`) — на всех переходах, включая возврат
после ошибки: иначе есть миг, когда записи нет ни в одном боксе, и правило
порядка показаний или привязанный осмотр её не видят. По той же логике
`deleteRejectedUsage` удаляет сначала привязанные осмотры, потом наработку.
Ручная синхронизация гоняет «наработка → осмотры» раундами, до трёх, пока
есть продвижение (`_flushUsageAndScans`): раунд разблокирует записи
следующего. Результат — по остатку обеих очередей вместе с «в полёте».
ad-hoc задачи уходят параллельно.

**Порядок показаний по оборудованию [ЖЁСТКО].** Наработка уходит двумя
очередями (отдельная `UsageUpdate` и `Scan.usageUpdates`), а разбираются они
в порядке ключей бокса. Запись не уходит, пока по тому же оборудованию есть
более раннее неотправленное и неотклонённое показание в любой из них
(`isUsageOrderBlocked` → чистое правило `hasEarlierUsage` в
`data/usage_order.dart`): иначе старое значение откатило бы счётчик. Время —
`Scan.createdAt` / `UsageUpdate.createdAt` (время открытия карточки); записи
прошлой версии без времени — самые ранние. Осмотр ТО со своей наработкой
старый признак «ждать наработку» (`maintenance_task_*`) не получает.

**Записи прошлой версии «только наработка»** привязаны к наработке через
`Scan.usageKeys` (ключи `UsageUpdate.key()`): очередь держит такой осмотр, пока
хоть одна из этих записей лежит в `usage_scans` / `pending_usage_scans`, в том
числе отклонённая; `deleteRejectedUsage` удаляет и привязанный осмотр. Новые
осмотры несут показания в себе (`usageUpdates`) и в этом не нуждаются.

**Отказ по существу помечается прямо в записи** — `Scan.lastError` (+
`lastShortages` при нехватке ЗИП) и `UsageUpdate.lastError`. Такая запись
автоматически больше не отправляется: решает обходчик — на главном хабе горит
полоса, у осмотра открывается экран разрешения конфликта, у наработки — лист
«повторить / удалить». Отметка **не входит в `key()`**, иначе запись потерялась
бы в боксе.

**Отказы по модели доступа** — `AccessDeniedException` (наследник
`ServerFailureException`, `code` из тела 403/409; разбирают `_throwServerError`,
`sendScan`, `uploadRepairPhotos`). Два вида, и причина пишется **своей
строкой**, а не текстом сервера — по ней экраны и очередь узнают вид отказа:
- `inspection_closed_by_other` — задачу уже **закрыл** другой исполнитель.
  Окончательно: `ScanQueueStrings.errorClosedByOther`, экран разбора осмотра
  прячет «Повторить» и предлагает удалить. Склад локально не уменьшается —
  списания не было;
- `already_taken` — задачу **взял** другой, но не закрыл; её могут
  переназначить обратно. `ScanQueueStrings.errorTakenByOther`, «Повторить
  отправку» остаётся, подсказка — уточнить у руководителя;
- записи прошлой версии, где оба конфликта писались одной строкой
  (`errorTakenOrClosedLegacy`), — какой был, неизвестно. Повтор доступен:
  сервер ответит точным кодом, и причина заменится окончательной или запись
  уйдёт;
- `permission_denied`, `direction_denied`, `division_denied` — у роли нет права.
  Поправимо: `ScanQueueStrings.errorNoRights` / `repairNoRightsMessage`. Когда
  версия доступа меняется (вход или `syncAccessProfile`),
  `retryNoRightsRejections` снимает такие пометки со всех очередей — записи
  уходят сами; нет права по-прежнему — встанут обратно до следующей смены.
  У правки ремонта при этом ремонт не перечитывается: без права ответ «нет
  доступа к ремонту» превратился бы в окончательное «передан другому».

**Заявка «Другое»** — два запроса: создание задачи (`createPeriodicTask`) и
её фото (`uploadPeriodicTaskPhotos`), оба с постоянным `Idempotency-Key`. Ключ
— `PeriodicTaskRequest.eventId` (у записей прошлой версии — от `key()`), у фото
свой: `<ключ>:photos`. Сервер сверяет ключ с телом запроса, поэтому
`toJson()` от повтора к повтору не меняется. Uuid созданной задачи пишется в
запись (`serverUuid`) **до** загрузки фото: сорвалась загрузка — повтор идёт
сразу к фото, второй задачи не будет. Что повторять, решает
`isRetryableProblemPhotoError` (`data/problem_report_photos.dart`): обрыв,
5xx, протухший доступ — повтор через 120 с; 409 (задачу уже взяли — фото
сообщения о проблеме сервер больше не принимает), 403, 404, 413, 422 —
снимки бросаются с записью в журнал, заявка доставлена; те же кадры уходят в
самом осмотре. 410 и 409 на создании (`isProblemReportSettled`) — задачу по
ключу удалили, такая задача уже есть или ключ использован с другим телом:
повтор ответит тем же, запись убирается с записью в журнал.
Фото сервер принимает от автора заявки по `inspection.create`, пока задачу не
взяли, и по `tasks.edit`. Сервер прошлой версии ключ не знает и фото
принимает только по `tasks.edit`.

Известный пробел: у очереди ad-hoc задач пометки отказа нет вовсе — её `catch`
возвращает запись в pending, и отказ **создания** по правам повторяется каждые
120 секунд. Модель `PeriodicTaskRequest` поля под причину не имеет.

**Схема Б — с побочным эффектом** (ремонты: сервер меняет состояние
оборудования и шлёт уведомления):

```
pendingRepairBox ──► createRepair(Idempotency-Key = localId)
                          │  serverUuid пишется в бокс СРАЗУ, до фото
                          ▼
                     фото по одному, у каждого свой ключ
                          ▼
                     updateRepair(расход + комментарий [+ статус])
                          ▼
                     upsertRepair() + удалить черновик
```

- пары `pending_` нет — от дубля защищает сервер по ключу;
- **отказ ≠ отсутствие связи**: `isRetryableRepairError` разделяет их. Нет
  связи — попытка не засчитывается; сервер отказал — причина пишется в черновик
  по-русски, автоповторов больше нет, решает обходчик;
- конфликт «оборудование уже в ремонте» доискивает занявший ремонт
  (`_findBlockingRepair`) — данные для экрана разрешения.

**Проверка связи** — `GlobalState.hasConnectionToServer`: `isAlive()` (GET
`/v1/system/ping`, на 404 — `/docs`; таймаут 5 с) с кэшем на 10 секунд. `connectivity_plus` есть в
зависимостях, но код закомментирован — доступность определяется **только**
пингом сервера, не состоянием сети. Отдельно от этого работает окно
недоступности в `API` (30 с, ставится по любому неудавшемуся запросу) — это
разные механизмы: первый отвечает на вопрос «идти ли вообще», второй мгновенно
отказывает, пока идти бесполезно.

## SSE и push

**Контракт: SSE — только сигнал, источник правды REST.** Событие `ping`
игнорируется. Так же описано в `sampo_smart_backend/docs/mobile_notifications_flow.md`.

Два независимых потребителя одного стрима: `NotificationsService` в main-изоляте
(обновляет список) и `NotificationsTaskHandler` в изоляте foreground-сервиса
(показывает локальные уведомления, дедуп по `notification_uuid`). Парсинг общий
— `SseLineParser`.

**Смена доступа на лету.** Сервер узнаёт о новой роли, правах или области на
следующем же запросе; приложение — тремя путями, все сходятся в
`DataProvider.refreshAccess` (секунда склейки → `syncAccessProfile` →
`mainSyncFresh`):
- заголовок `X-Access-Version` на **каждом** ответе общего клиента
  (`API.onAccessVersion` → `handleAccessVersion`): версия не та, что в
  профиле, и токен запроса — текущей сессии (`isLiveAccessSession`,
  проверка внутри фиксации: ответ, пришедший после выхода, входа другим или
  блокировки этой сессии, выбрасывается целиком). Сессия сравнивается и по
  номеру (`startAccessSession` — в сеттере `GlobalState.authUser` и во входе
  до сохранения профиля): токен повторного входа может совпасть с прежним, и
  по нему одному запрос прошлой сессии не отличить. Общий клиент запоминает
  номер при отправке (`API.accessSession`) и передаёт его вместе с токеном в
  `onAccessVersion` и `onAccessBlocked`. Два параллельных запроса
  одной сессии упорядочивает `AccessResponseOrder`: номер берётся до
  запроса, и ответ более раннего не ложится поверх более позднего —
  `access_version` непрозрачна, по ней порядок не определить;
- SSE `notification` с `action: access_changed` в main-изоляте; в изоляте
  foreground-сервиса — пуш не показывается, а в main уходит
  `{'type': 'access_changed'}`. Поток сервер после этого закрывает,
  переподключение получает новую область;
- фоновая синхронизация раз в минуту (`syncAccessProfile` в `mainSync`) —
  запасной путь.
Курсоры инкрементальных справочников при этом не сбрасываются вручную —
сервер ответит `resync_required` (см. «Инкрементальные справочники»). Карточка
ремонта, ушедшего из области (403 «нет права», «нет доступа к ремонту», 404),
показывает «Нет доступа к ремонту», если на ней нет неотправленной правки
(`isRepairOutOfScope`).

Push **без FCM**: `flutter_foreground_task` + локальные уведомления. IPC в
изолят — через `FlutterForegroundTask.saveData` (`sse_base_url`, `sse_jwt`,
`push_tap_pending`), обратно — `sendDataToMain`.

Стрим закрывается через `StreamedResponseHandle.close()` — иначе соединение
течёт.

`PushNotificationsController.start()` и `stop()` выполняются **строго по
очереди** (`_serialized`): иначе запуск нового аккаунта пересекался со
старой остановкой (выход при блокировке не ждёт её), и та останавливала
сервис или стирала токен нового. Проверки авторизации — в момент
выполнения, а не вызова. Watchdog `stop()` гасит сразу, до очереди.

## Прочие интеграции

`mobile_scanner` (QR, beta-версия в проде), `image_picker`,
`flutter_inappwebview` (база знаний), `url_launcher`, `video_player`
(онбординг), `flutter_svg`, `flutter_markdown`, `awesome_dialog`, `crypto`
(md5 для ключей очереди), Shorebird (code push).

`crypto` и `http_parser` до августа 2026 импортировались напрямую, но в
`pubspec.yaml` не значились — приходили транзитивно. Объявлены явно после того,
как включённый линтер это заметил (`depend_on_referenced_packages`).

**Не используются:** `dio`, `cached_network_image`, `shared_preferences`,
`connectivity_plus`, `infinite_scroll_pagination`, `flutter_pdfview`,
`gallery_saver_plus`, `file_picker`, `mime`, `themed`, `cherry_toast`,
`qr_code_scanner_plus`, `flutter_screenutil` (один вызов). Не бери их как
«уже есть».

Аналитики и крашрепортинга нет. Deep links, платежей, карт нет.

## Границы безопасности

| Что | Состояние |
|---|---|
| JWT | В Hive, без шифрования, внутри объекта `User` |
| Пароль пользователя | В Hive **открытым текстом** — нужен для офлайн-входа |
| `.env` | В `.gitignore` и вне индекса git, но **включён в assets** и попадает в APK |
| Ключи подписи | Пути и пароли в `.env`; keystore в git не попадает |
| Шифрование Hive, certificate pinning | Нет |
| `android:allowBackup` | `false` — данные не уходят в облачный бэкап |

**Никогда не выводи значения из `.env`, JWT или пароли в код, документацию,
сообщения об ошибках или коммиты.**
