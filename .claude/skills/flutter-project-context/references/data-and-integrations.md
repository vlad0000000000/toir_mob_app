# Данные и интеграции

## Бэкенд

Единственный внешний API — **Sampo Smart** (FastAPI, репозиторий
`sampo_smart_backend` в том же workspace). Базовый URL из `.env`
(`API_ENDPOINT`), читается один раз при старте — смена адреса требует
перезапуска.

`API.baseUrl` **срезает завершающие слеши** на входе. Это не косметика: все
методы клеят путь как `'$baseUrl/v1/...'`, и слеш в конфиге давал
`https://host//v1/...`, на что бэкенд отвечает 404 — отваливалось всё, включая
`isAlive()`, и приложение показывало «нет соединения» при живом сервере.

HTTP-клиент — **`package:http`**. `dio` в зависимостях есть, не используется.

### Организация

```
http/api.dart          ядро: baseUrl, jwtToken, таймауты, _client, окно
                       недоступности, _guardOffline, isAlive, разбор detail
  part auth_api        part equipment_api    part task_api
  part scan_api        part notifications_api
  part repair_api      part spare_part_api   part ppr_api
```

`API` фактически stateless — всё состояние в статиках, инстансы создаются
свободно: `API()`.

### **[ЖЁСТКО]** Общий клиент и окно недоступности

Все запросы приложения идут через **`_client`** — `_OfflineAwareClient` поверх
`IOClient` с `connectionTimeout` 3 с. Top-level `http.get/post` в методах API не
место: они поднимают собственный клиент мимо этого таймаута и, главное, мимо
отметки о недоступности. Пять таких вызовов уже пережили переход на общий
клиент и вели себя заметно — успешный запрос мимо обёртки не снимал отметку.

Как устроена отметка (`api.dart`):

- запрос не доехал (`isOfflineError`) → `API.markServerUnreachable()`, сеть
  закрыта на `API.offlineWindow` = **30 секунд**;
- пока окно стоит, `_client` мгновенно бросает `SocketException` того же вида,
  что при реальном обрыве — очередь и экраны уже умеют его разбирать;
- любой ответ сервера снимает окно (`markServerReachable`);
- пинг живости идёт через отдельный **`_probeClient`** и окно игнорирует —
  иначе выйти из него было бы нечем;
- явное действие обходчика (вход, «Синхронизировать данные», «Повторить»)
  вызывает `API.retryConnectionNow()`: отвечать «связи нет» по памяти
  полуминутной давности нельзя.

Таймауты: `_readTimeout` **8 с** (GET, мелкие записи, login), `_uploadTimeout`
60 с (multipart), `_aliveTimeout` 5 с (`isAlive`).

**Пагинация:** параметр URL `skip`, аргумент метода `offset`. Цикл выходит на
неполной странице (`length < limit`), а не на пустой — иначе каждый справочник
делал бы лишний round-trip.

**Фильтруй на сервере.** Открытые задачи качались по всей компании и
отбирались на телефоне, пока не начали передавать `responsible_user_uuids`.
Плановые (`status=scheduled`) до сих пор качаются целиком — отбор по должности
идёт на клиенте, серверного фильтра нет.

### Заголовки, кодировка, multipart

Состав задач у ППР отдаёт только детальный ответ, поэтому `getActivePprs()`
делает N+1 запрос — осознанно: активных ППР немного. Отказ на любых деталях
обрывает **всю** синхронизацию ППР: пропустить один — значит убрать его задачи
из списков до следующего удачного прохода, а сохранённый снимок остался бы цел.

- `Authorization: Bearer {jwt}` — везде, кроме `login` и `isAlive`.
- Каждый GET декодируется вручную через `Utf8Decoder(allowMalformed: true)` —
  защита от битой кириллицы. Не заменяй на `response.body`.
- Multipart: `sendScan`, `updateEquipmentState`, фото периодической задачи,
  `uploadRepairPhotos`. Фото передаются base64-строками и декодируются перед
  отправкой; битый кадр логируется и пропускается, отправка не срывается.
- **Снимки ремонта в очереди — файлы на диске** (`data/repair_photo_files.dart`),
  а не base64 в Hive: черновик может ждать связи сутками. Уходят **по одному
  запросу на кадр** — сервер принимает список, но при обрыве на середине узнать,
  что сохранилось, было бы неоткуда.

### Что сервер делает за клиента (ремонты)

1. Сужает выдачу `/v1/repairs/` до ремонтов пользователя и его должности.
2. Ставит оборудованию `in_repair` при создании ремонта и возвращает прежнее
   состояние при закрытии.
3. Белый список полей PATCH для роли `walker`: `status`, `comment`,
   `actual_consumptions`. Лишнее поле → 403. Исключение — захват свободного
   ролевого ремонта одиночным `responsible_user_uuid`.

### Что сервер делает за клиента (расход ЗИП по осмотру)

`PATCH /v1/company/fault_inspections/{uuid}` принимает поле формы
`actual_consumptions` и **сам списывает склад** при приёме осмотра. Не хватило
остатка — 409 с машиночитаемым телом: `detail_code: "insufficient_stock"` и
`shortages` вида `{spare_part_uuid, spare_part_name, required, available}`.
Клиент разбирает его в `InsufficientStockException` и хранит вместе с осмотром
(`Scan.lastShortages`), потому что экран разрешения конфликта открывается и
через сутки без связи.

Расход можно указать и по задаче, для которой норму в админке не выбирали: оба
прежних запрета (блок `spare_part_usage` только у настроенных задач и отказ
PATCH по остальным) сняты.

### Идемпотентность

`createRepair` и `uploadRepairPhotos` принимают `Idempotency-Key`; сервер помнит
пару «компания + ключ» и на повтор возвращает уже созданную сущность с кодом
200. На этом держится офлайн-очередь ремонтов. Пустую строку сервер считает
ошибкой — заголовок ставится только при непустом ключе.

## Аутентификация

JWT Bearer. `POST /v1/auth/login` → `GET /v1/user/me`. `User` кладётся в бокс
`users` под ключом `username` и отдельно под `auth_user` — это и есть текущий
пользователь. `API.jwtToken` — геттер по `GlobalState.authUser`.

**Refresh-токенов нет.** Есть частичная обработка 401: `_throwServerError`
выделяет его в `AuthExpiredException`, и очередь ремонтов отличает «сервер
отказал» от «протух токен» — черновик не помечается отклонённым, поднимается
флаг `DataProvider.authExpired`, список показывает баннер. Автоматического
выхода на `/login` нет. Остальные методы превращают 401 в обычный `Exception`,
который `sync*` проглотит.

**Офлайн-вход** сравнивает пароль с локально сохранённым — **пароль лежит в
Hive открытым текстом**. Осознанный компромисс, шифрования Hive нет.

Роль `walker` — единственный допуск. `effectiveRole` и `customRoleId`
используются для фильтрации задач и наработки, экранов не ограничивают.

## Локальное хранилище — Hive

### Расположение

`HiveStorageLocation.resolve(packageInfo)` (`data/hive_storage_location.dart`),
вызов в `main.dart`. Имя каталога — md5 от `appName|packageName`, **без версии**,
поэтому обновление приложения базу не обнуляет.

Прежняя схема включала версию, и каждый выпуск открывал пустую базу —
неотправленные осмотры исчезали. `resolve` при первом запуске переносит `*.hive`
из каталога старой схемы и ставит маркер `.migrated` **только после полного
успеха** — прерванный перенос повторится целиком.

Шифрования нет.

### Кэш в памяти

`DataProvider` при конструировании поднимает часть боксов в списки; UI читает
**их**, а не боксы. После записи в бокс синхронизируй кэш
(`updateInventoryRecords()`, `_rebuildSparePartIndex()`). Забыть об этом —
типовая ошибка: в Hive обновилось, на экране старое.

## Синхронизация

**Модель: сервер перезаписывает справочники, клиент владеет очередью.**

| Направление | Стратегия |
|---|---|
| Каталог ЗИП | Инкрементально: окно `updated_since` + список удалённых. Полная перезапись — только на первом проходе и после сбоя. Входит в `mainSync`. См. ниже |
| ППР | Список актуальных + детали каждого; снимок JSON-строкой в `stringBox`, осмотры задач ППР догружаются поштучно |
| Остальные справочники | Полная перезапись: `box.clear()` + `addAll()`. ETag нет нигде |
| Осмотры, наработки, ad-hoc задачи | Очередь в Hive с ретраями до успеха |
| Черновики и правки ремонтов | Очередь с `Idempotency-Key` вместо таймаута возврата |
| Активные ремонты | Кэшируются — карточку можно открыть и править без сети |
| Закрытые ремонты, история движения ЗИП, уведомления | **Не кэшируются** |
| Состояние оборудования | Отправляется сразу, в очередь не ставится. Исключение — «В ремонте»: идёт через создание ремонта и потому переживает офлайн |

### `mainSync()`, ППР и каталог ЗИП

`mainSync()` тянет десять справочников **параллельно** (`Future.wait`), каждый
глотает свою ошибку. Триггеры: фоновый цикл раз в 60 с, вход в «Задачи», «ППР»,
«Сканер», «Осмотр оборудования», после отправки осмотра, после логина.

**Пара «ППР → задачи» — единственная последовательная:** `syncTasks()` по
составу ППР догружает его осмотры и пишет всё в бокс задач одной операцией,
поэтому `syncPpr()` обязан завершиться раньше. Внутри `Future.wait` они идут как
`syncPpr().then((_) => syncTasks())` — параллельно со всем остальным.

**Пока стоит отметка недоступности, `mainSync` не начинается вовсе**
(`API.isServerKnownUnreachable`): десять параллельных проходов, часть из них
постраничные, и каждая страница ждала своего таймаута.

**Каталог ЗИП снова внутри `mainSync`** — после перевода на инкрементальный
проход это один запрос с пустым ответом. Его исключали, когда каждый проход
перекачивал десятки тысяч позиций сотнями страниц, но за это остатки на складе
отставали: обновлялись раз в десять минут или вручную, и в расходе по ремонту
обходчик видел вчерашние числа. Полным проход бывает только на первом заходе и
после оборванной записи — худший случай остался прежним, но разовым.

`ensureSparePartsLoaded()` остался для экранов, которым каталог нужен сразу
(раздел ЗИП, список и карточка ремонта, экран конфликта осмотра): грузит,
только если кэш пуст, экран не ждёт. Кнопка «Синхронизировать данные» тянет
каталог всегда.

У `syncSpareParts` есть защита от параллельного запуска: второй вызов
присоединяется к идущему. **У остальных `sync*` такой защиты нет**, хотя
наложение возможно — это открытый риск.

#### Инкрементальный проход каталога ЗИП

Единственный справочник, который **не** перезаписывается целиком. Сервер принимает
`updated_since` и `sync_until` (оба UTC) и отвечает не списком, а объектом:

```json
{ "items": [...], "deleted": [{"uuid": "...", "deleted_at": "..."}], "sync_until": "..." }
```

Как это устроено на клиенте (`data_provider_sync.dart`):

- **Курсор** — `spare_parts_cursor` в `stringBox`, серверный `sync_until` прошлого
  прохода. Отдельно от `spare_parts_sync_at`: та отметка — локальное время для
  подписи «Остатки на …». В окно запроса местное «сейчас» подставлять нельзя,
  часы телефона и сервера расходятся.
- **Полный проход** — когда курсора нет, бокс пуст или прошлая запись оборвалась.
  Идёт как окно «с 1970 года»: тем же запросом приходит `sync_until`, иначе
  курсор было бы неоткуда взять. Он же переводит бокс на **ключи по uuid** —
  раньше ключи были автоинкрементными, и точечное обновление было невозможно.
- **Инкрементальный проход** — окно от курсора; `sync_until` первой страницы
  закрепляется и передаётся в остальные, иначе позиция, изменившаяся между
  запросами, съехала бы на уже прочитанную страницу.
- **Удаления** — из `deleted`: сервер ведёт таблицу «надгробий» и туда же кладёт
  заархивированные интеграцией. Без этого списка удалённая позиция осталась бы
  в хранилище навсегда.
- **Откат** — если `sync_until` в ответе нет (сервер режим не понимает), клиент
  возвращается к полному проходу.
- **Курсор двигается последним**: оборванный проход повторит то же окно, а повтор
  безвреден — записи кладутся по ключу, удаление уже удалённого ничего не делает.
- **Порядок на диске больше не отсортирован**, поэтому каталог сортируется в
  памяти: в конструкторе `DataProvider` на старте и после каждого прохода.

Остальные шесть эндпоинтов (оборудование, неисправности, осмотры, нормы, ППР,
ремонты) `updated_since` тоже принимают, но клиент их пока качает целиком.

### Очереди отправки

Цикл отправляет осмотры, наработки, ad-hoc задачи, черновики ремонтов и
отложенные правки. Просыпается через **5 → 15 → 60 секунд**: пока сервер помечен
недоступным, шаг растёт (`_outboxBackoffSeconds`) — без бэкоффа цикл долбился в
мёртвый сервер каждые пять секунд весь день. Перед проходом три отсечки: окно
недоступности, `GlobalState.isAuthorized` (иначе `Exception('Not authenticated')`
принимался бы за отказ по существу и осмотр помечался отклонённым) и
`_outboxIsEmpty` — очереди почти всегда пусты.

**Схема А — без побочного эффекта** (осмотры, наработки, задачи):
запись перекладывается в `pending_`, при неуспехе возвращается через **120
секунд** (комментарии в коде местами говорят «60» — верь коду).

Тонкости: `_isSyncingScans` защищает от двойной отправки; задача ТО не уходит,
пока по её оборудованию висит непустая очередь наработки (сервер пересчитывает
следующее ТО от счётчика); на старте `pending_scans` целиком возвращается в
`scans`.

**Отказ по существу помечается прямо в записи** — `Scan.lastError` (+
`lastShortages` при нехватке ЗИП) и `UsageUpdate.lastError`. Такая запись
автоматически больше не отправляется: решает обходчик — на главном хабе горит
полоса, у осмотра открывается экран разрешения конфликта, у наработки — лист
«повторить / удалить». Отметка **не входит в `key()`**, иначе запись потерялась
бы в боксе.

**Схема Б — с побочным эффектом** (ремонты: сервер меняет состояние
оборудования и шлёт уведомления):

```
pendingRepairBox ──► createRepair(Idempotency-Key = localId)
                          │  serverUuid пишется в бокс СРАЗУ, до фото
                          ▼
                     фото по одному, у каждого свой ключ
                          ▼
                     updateRepair(расход + комментарий [+ статус])
                          ▼
                     upsertRepair() + удалить черновик
```

- пары `pending_` нет — от дубля защищает сервер по ключу;
- **отказ ≠ отсутствие связи**: `isRetryableRepairError` разделяет их. Нет
  связи — попытка не засчитывается; сервер отказал — причина пишется в черновик
  по-русски, автоповторов больше нет, решает обходчик;
- конфликт «оборудование уже в ремонте» доискивает занявший ремонт
  (`_findBlockingRepair`) — данные для экрана разрешения.

**Проверка связи** — `GlobalState.hasConnectionToServer`: `isAlive()` (GET
`/docs`, таймаут 5 с) с кэшем на 10 секунд. `connectivity_plus` есть в
зависимостях, но код закомментирован — доступность определяется **только**
пингом сервера, не состоянием сети. Отдельно от этого работает окно
недоступности в `API` (30 с, ставится по любому неудавшемуся запросу) — это
разные механизмы: первый отвечает на вопрос «идти ли вообще», второй мгновенно
отказывает, пока идти бесполезно.

## SSE и push

**Контракт: SSE — только сигнал, источник правды REST.** Событие `ping`
игнорируется. Так же описано в `sampo_smart_backend/docs/mobile_notifications_flow.md`.

Два независимых потребителя одного стрима: `NotificationsService` в main-изоляте
(обновляет список) и `NotificationsTaskHandler` в изоляте foreground-сервиса
(показывает локальные уведомления, дедуп по `notification_uuid`). Парсинг общий
— `SseLineParser`.

Push **без FCM**: `flutter_foreground_task` + локальные уведомления. IPC в
изолят — через `FlutterForegroundTask.saveData` (`sse_base_url`, `sse_jwt`,
`push_tap_pending`), обратно — `sendDataToMain`.

Стрим закрывается через `StreamedResponseHandle.close()` — иначе соединение
течёт.

## Прочие интеграции

`mobile_scanner` (QR, beta-версия в проде), `image_picker`,
`flutter_inappwebview` (база знаний), `url_launcher`, `video_player`
(онбординг), `flutter_svg`, `flutter_markdown`, `awesome_dialog`, `crypto`
(md5 для ключей очереди), Shorebird (code push).

`pubspec.yaml` не значились — приходили транзитивно. Объявлены явно после того,
как включённый линтер это заметил (`depend_on_referenced_packages`).

**Не используются:** `dio`, `cached_network_image`, `shared_preferences`,
`connectivity_plus`, `infinite_scroll_pagination`, `flutter_pdfview`,
`gallery_saver_plus`, `file_picker`, `mime`, `themed`, `cherry_toast`,
`qr_code_scanner_plus`, `flutter_screenutil` (один вызов). Не бери их как
«уже есть».

Аналитики и крашрепортинга нет. Deep links, платежей, карт нет.

## Границы безопасности

| Что | Состояние |
|---|---|
| JWT | В Hive, без шифрования, внутри объекта `User` |
| Пароль пользователя | В Hive **открытым текстом** — нужен для офлайн-входа |
| `.env` | В `.gitignore` и вне индекса git, но **включён в assets** и попадает в APK |
| Ключи подписи | Пути и пароли в `.env`; keystore в git не попадает |
| Шифрование Hive, certificate pinning | Нет |
| `android:allowBackup` | `false` — данные не уходят в облачный бэкап |

**Никогда не выводи значения из `.env`, JWT или пароли в код, документацию,
сообщения об ошибках или коммиты.**
