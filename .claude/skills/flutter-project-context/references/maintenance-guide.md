# Как поддерживать этот скилл

Скилл описывает **стабильное знание**. Не журнал задач и не список дел. Факт
перестал быть верным — правь скилл в том же изменении, которое его сломало.

---

## Когда обновлять обязательно

| Изменение | Обновить |
|---|---|
| Добавлена/удалена крупная фича или экран | `features-and-flows.md`, `project-overview.md`, `SKILL.md` (карта, если появилась папка) |
| Изменён список маршрутов или способ навигации | `architecture.md`, `features-and-flows.md` |
| Новый подход к состоянию или к получению зависимостей | `architecture.md`, `code-conventions.md` |
| Новый эндпоинт, изменён контракт | `data-and-integrations.md` |
| Новый бокс, `typeId` или поле модели | `data-and-integrations.md`, `code-conventions.md`, `SKILL.md` (факт 1) |
| Изменена дизайн-система, появилось семейство компонентов | `ui-ux-system.md` |
| Изменена стратегия синхронизации или очередей | `data-and-integrations.md`, `architecture.md` |
| Новые ключи `.env`, изменён процесс сборки | `testing-build-and-release.md`, `project-overview.md` |
| Починен линтер, заведены тесты | `SKILL.md`, `code-conventions.md`, `testing-build-and-release.md` |
| Удалён или оживлён мёртвый код | `architecture.md`, `ui-ux-system.md`, `evidence-and-unknowns.md` |
| Новый термин домена | `project-glossary.md` |
| Разрешён открытый вопрос | `evidence-and-unknowns.md` — перенести в факты |

## Когда **не** надо

Обычная правка бага внутри экрана без смены паттерна; косметика;
переименование локальной переменной; временное состояние; детали конкретной
задачи или ветки.

**Отсечка: если факт перестанет быть верным через месяц — ему здесь не место.**

---

## Процедура

1. Посмотри, что реально изменилось: `git status`, `git diff`,
   `git log --oneline -20`.
2. Отдели стабильное знание от деталей задачи: «понадобится ли это тому, кто
   через полгода откроет проект впервые?»
3. Правь только затронутые справочники, не переписывай файл целиком ради строки.
4. **Удаляй устаревшее.** Не оставляй «раньше было так, теперь так» — скилл
   описывает настоящее. История живёт в git.
5. Проверь, что упомянутые пути существуют:
   ```bash
   grep -rhoE '(lib|test|android|ios|assets)/[A-Za-z0-9_./-]+\.(dart|yaml|gradle|xml|md|kt|json)' \
     .claude/skills/flutter-project-context \
     | sort -u | while read p; do [ -e "$p" ] || echo "MISSING: $p"; done
   ```
6. Обнови дату и хеш в шапке `evidence-and-unknowns.md`:
   `git log -1 --format='%h %ad' --date=short`.
7. Проверь, что не утекли секреты:
   ```bash
   grep -rniE 'password|secret|token|api_key|keystore|jwt' .claude/skills/flutter-project-context
   ```
   Упоминание **имени** переменной допустимо, **значения** — нет.

## Гигиена содержания

- Существенное утверждение — с путём к файлу.
- Никаких общих фраз: не «следуй чистой архитектуре», а «метод API пишется как
  extension на `API` в part-файле, см. `equipment_api.dart`».
- Помечай силу правила: `[ЖЁСТКО]` / `[ДОМИНИРУЕТ]` / `[ЛЕГАСИ]`.
- Противоречия не сглаживай: назови оба варианта и дай рекомендацию.
- **`SKILL.md` держи коротким** — он загружается всегда. Ориентир ≤ 200 строк,
  всё объёмное в `references/`.
- Не дублируй: факт живёт в одном справочнике, в остальных — ссылка.
- Не копируй большие куски исходников: 5–15 строк как шаблон достаточно.

**`name` и `description` во frontmatter менять нельзя** — `description`
намеренно написан широко, чтобы скилл подхватывался автоматически для любых
задач по проекту. Сужение сломает автозапуск.

## Структура

```
SKILL.md                      порядок работы, правила решений, критические факты, карта
references/
  project-overview.md         продукт, роли, сущности, ограничения
  architecture.md             слои, состояние, навигация, потоки, легаси
  features-and-flows.md       экраны, сценарии, обработанные и необработанные случаи
  code-conventions.md         именование, импорты, модели, HTTP, ошибки, образцы
  ui-ux-system.md             токены, тема, компоненты, паттерны, состояния
  data-and-integrations.md    API, Hive, синхронизация, очереди, SSE, безопасность
  testing-build-and-release.md версии, .env, команды, сборка, ограничения
  project-glossary.md         термины и что с чем путают
  evidence-and-unknowns.md    проверенное, противоречия, открытые вопросы
  maintenance-guide.md        этот файл
```

Новый справочник заводи, только если тема не помещается ни в один существующий
и объёмна. Добавив файл, пропиши его в таблицу «Какой справочник читать» в
`SKILL.md` и в это дерево.

## Что устареет первым

1. Списки мёртвого кода — при первой же чистке.
2. Эталон `flutter analyze = 106 info` — он поедет вниз, как только возьмутся
   разбирать наследство, и вверх при добавлении кода.
3. Число тестов (122 в 19 файлах).
4. Таблица эндпоинтов — растёт вместе с бэкендом.
5. Списки боксов (21) и `typeId` (занято 0–4, 6–29) — при добавлении модели.
6. Таблица маршрутов (22 штуки) и ветки `app_bar.dart`.
7. Открытые вопросы в `evidence-and-unknowns.md`.
