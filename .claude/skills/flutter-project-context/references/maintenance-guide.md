# Как поддерживать этот скилл

Скилл описывает **стабильное знание** о проекте. Он не журнал задач и не список
дел. Если факт перестал быть верным — правь скилл в том же изменении, которое
его сломало.

---

## Когда обновлять — обязательно

Задача осознанно изменила что-то из этого списка → обнови соответствующий
справочник **в том же цикле работы**, до отчёта о завершении.

| Изменение | Обновить |
|---|---|
| Добавлена/удалена крупная фича или экран | `features-and-flows.md`, `project-overview.md` (список фич), `SKILL.md` (карта репозитория, если появилась новая папка) |
| Изменён список маршрутов, `redirect` или способ навигации | `architecture.md` (таблица маршрутов, раздел «Навигация»), `features-and-flows.md` (иерархия) |
| Заменён или добавлен подход к управлению состоянием | `architecture.md` (раздел «Управление состоянием»), `code-conventions.md` |
| Появился DI-контейнер или новый способ получения зависимостей | `architecture.md` (раздел «Внедрение зависимостей») |
| Новый HTTP-эндпоинт, изменён контракт, добавлена интеграция | `data-and-integrations.md` (таблица эндпоинтов) |
| Изменена схема Hive: новый бокс, новый `typeId`, новое поле модели | `data-and-integrations.md` (таблицы боксов и `stringBox`), `SKILL.md` (п. 1 «пять фактов»), `code-conventions.md` |
| Изменена дизайн-система: токены, палитра, новая тема | `ui-ux-system.md`, `SKILL.md` при необходимости |
| Появилось семейство переиспользуемых компонентов | `ui-ux-system.md` (таблица компонентов), `code-conventions.md` (образцы) |
| Изменена стратегия локализации | `code-conventions.md` (раздел «Локализация»), `project-overview.md` (ограничения) |
| Появились флейворы, `--dart-define`, новые ключи `.env` | `testing-build-and-release.md`, `project-overview.md` (таблица флагов) |
| Изменён процесс сборки, релиза, CI | `testing-build-and-release.md` |
| Заведены тесты / изменился их запуск | `testing-build-and-release.md`, `code-conventions.md` (раздел «Тесты»), `SKILL.md` (п. 5 «пять фактов») |
| Обновлён Flutter/Dart/AGP/Kotlin/JDK | `testing-build-and-release.md` (таблица версий) |
| Починен или включён линтер | `SKILL.md` (п. 4), `code-conventions.md` (предупреждение в шапке), `testing-build-and-release.md` |
| Удалён/оживлён мёртвый код из списков | `architecture.md` («Легаси и исключения»), `ui-ux-system.md`, `evidence-and-unknowns.md` |
| Появился новый термин домена | `project-glossary.md` |
| Разрешён один из открытых вопросов | `evidence-and-unknowns.md` (перенести из «вопросов» в факты) |

## Когда обновлять — **не** надо

- Обычная правка бага внутри существующего экрана без смены паттерна.
- Косметика, переименование локальной переменной, форматирование.
- Временное состояние («сегодня сборка падает», «жду ответа заказчика»).
- Детали конкретной задачи, ветки, тикета.
- Что-то, что уже полностью выводится из кода за 30 секунд чтения.

Правило отсечки: **если факт перестанет быть верным через месяц — ему здесь
не место.**

## Процедура обновления

1. **Посмотри, что реально изменилось.**
   ```bash
   git status
   git diff              # незакоммиченное
   git log --oneline -20 # с момента последнего обновления скилла
   ```
2. **Отдели стабильное знание от деталей задачи.** Спроси: «понадобится ли это
   тому, кто через полгода откроет проект впервые?»
3. **Правь только затронутые справочники.** Не переписывай файл целиком ради
   одной строки — это ломает читаемость диффа.
4. **Проверь, что все упомянутые пути ещё существуют.** Быстрая проверка:
   ```bash
   # вытащить упоминания файлов из скилла и проверить наличие
   grep -rhoE '(lib|test|android|ios|assets)/[A-Za-z0-9_./-]+\.(dart|yaml|gradle|xml|md|kt|json)' \
     .claude/skills/flutter-project-context \
     | sort -u | while read p; do [ -e "$p" ] || echo "MISSING: $p"; done
   ```
   Номера строк проверять построчно не обязательно, но если ты правил
   упомянутый файл — обнови и номер.
5. **Удали устаревшие утверждения.** Не оставляй «раньше было так, теперь так» —
   скилл описывает настоящее. История живёт в git и `REFACTORING_CHECKLIST.md`.
6. **Добавь новые unknown, если уверенности не хватает.** Лучше честная запись
   в `evidence-and-unknowns.md`, чем правдоподобная выдумка.
7. **Обнови дату анализа и хеш коммита** в шапке `evidence-and-unknowns.md`:
   ```bash
   git log -1 --format='%H %ad' --date=short
   ```
   Это метка «когда сверялись», а **не** доказательство правильности.
8. **Проверь, что в скилл не утекли секреты**: значения из `.env`, JWT, пароли,
   ключи подписи, приватные URL.
   ```bash
   grep -rniE 'password|secret|token|api_key|keystore|jwt' \
     .claude/skills/flutter-project-context | grep -v 'название\|описан\|поле\|ключ\|переменн'
   ```
   Упоминание **имени** переменной допустимо, **значения** — нет.

## Гигиена содержания

- **Каждое существенное утверждение — с путём к файлу**, желательно со строкой:
  `lib/src/data/data_provider_outbox.dart:35-41`.
- **Никаких общих фраз.** Не «следуй чистой архитектуре», а «новый метод API
  пишется как extension на `API` в part-файле, см. `equipment_api.dart`».
- **Помечай силу правила** — `[ЖЁСТКО]` / `[ДОМИНИРУЕТ]` / `[СМЕШАНО]` /
  `[ЛЕГАСИ]`, как в `code-conventions.md`.
- **Противоречия не сглаживай.** Назови оба варианта, укажи доминирующий,
  дай рекомендацию.
- **`SKILL.md` держи коротким.** Он загружается всегда. Всё объёмное — в
  `references/`. Ориентир: `SKILL.md` ≤ ~200 строк.
- **Не дублируй.** Один факт живёт в одном справочнике; в остальных — ссылка.
  Например, правила Hive-адаптеров описаны в `code-conventions.md`, а
  `data-and-integrations.md` на них ссылается.
- **Не копируй большие куски исходников.** 5–15 строк как шаблон — достаточно.

## Проверка после правки скилла

```bash
# 1. Все файлы на месте
ls .claude/skills/flutter-project-context/
ls .claude/skills/flutter-project-context/references/

# 2. Frontmatter цел (name + description, без изменений в них)
head -5 .claude/skills/flutter-project-context/SKILL.md

# 3. Пути существуют (см. команду в п.4 выше)

# 4. Секретов нет (см. команду в п.8 выше)

# 5. Ничего лишнего не задето
git status --porcelain
```

**`name` и `description` в frontmatter менять нельзя** — `description`
специально написан широко, чтобы скилл подхватывался автоматически для любых
задач по проекту: фича, багфикс, рефакторинг, UI, UX, архитектура, интеграция,
тесты, локализация, сборка и релиз. Сужение формулировки сломает автозапуск.

## Структура файлов

```
.claude/skills/flutter-project-context/
├── SKILL.md                    краткий, операционный: порядок работы,
│                               правила решений, 5 критических фактов, карта
└── references/
    ├── project-overview.md        продукт, роли, сущности, платформы, ограничения
    ├── architecture.md            слои, состояние, DI, навигация, потоки, легаси
    ├── features-and-flows.md      экраны, маршруты, сценарии, edge cases
    ├── code-conventions.md        именование, импорты, виджеты, модели, ошибки
    ├── ui-ux-system.md            токены, тема, компоненты, состояния, паттерны
    ├── data-and-integrations.md   API, Hive, очереди, SSE, push, безопасность
    ├── testing-build-and-release.md  версии, .env, команды, сборка, релиз
    ├── project-glossary.md        термины, аббревиатуры, что с чем путают
    ├── evidence-and-unknowns.md   что проверено, противоречия, вопросы
    └── maintenance-guide.md       этот файл
```

Новый справочник заводи, только если тема не помещается ни в один существующий
и объёмна. Фича «Ремонты и ЗИП» пока описана внутри `features-and-flows.md`;
если её раздел разрастётся, выноси в `references/features/repairs.md`.
Добавив файл, пропиши его в таблицу «Какой справочник читать» в `SKILL.md`
и в это дерево.

## Что вероятно устареет первым

Следи за этими местами — они менее стабильны, чем остальное:

1. **Списки мёртвого кода** (`architecture.md`, `ui-ux-system.md`) — при первой
   же чистке.
2. **Эталонный вывод `flutter analyze` = 1 warning** — исчезнет, как только
   починят `analysis_options.yaml`.
3. **«Тестов нет»** — при появлении первого теста.
4. **Таблица эндпоинтов** — растёт вместе с бэкендом.
5. **Списки боксов и `typeId`** (занято 0–4, 6–28) — при добавлении модели.
6. **Открытые вопросы** в `evidence-and-unknowns.md` — по мере ответов.
7. **Таблица маршрутов** (21 штука) и ветки `app_bar.dart` — при добавлении
   экрана.
8. **Расхождения `ПЛАН_РЕМОНТЫ_ЗИП.md` с кодом** — если план однажды приведут
   в соответствие или удалят, раздел «Противоречия» надо чистить.
