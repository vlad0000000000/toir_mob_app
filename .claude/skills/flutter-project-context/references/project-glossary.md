# Глоссарий

Термины продукта, домена и кода этого репозитория. Русское слово, английский
идентификатор в коде и то, чем оно **не** является.

---

## Продукт и роли

**Обходчик** (`walker`) — единственный тип пользователя приложения. Рабочий,
физически обходящий оборудование. Проверка роли: `data_provider_remote.dart:151-156`.
Не путать с администратором — тот работает в веб-админке `sampo_smart_frontend`
и в приложение не пускается.

**Sampo Smart / ТОиР / enterprise54** — названия одной и той же системы:
бэкенд `sampo_smart_backend`, веб-админка `sampo_smart_frontend`, мобильное
приложение `sampo_smart_mobile`. В коде приложения продуктовое имя приходит из
`.env` (`APP_TITLE`).

**Обход** — рабочий цикл: прийти к оборудованию → отсканировать QR → закрыть
задачи / зафиксировать проблему / внести наработку → отправить.

**Компания** (`Company`) — арендатор системы. Приложение читает её ради тарифа
и фича-флага `allowRequestsWithoutQr`.

## Домен

**Оборудование / ТМЦ** (`InventoryRecord`, в API — `equipment`) — станок, узел или
товарно-материальная ценность. **Внимание на разнобой имён:** класс
`InventoryRecord`, бокс `inventory`, эндпоинт `/v1/company/equipment`, метод
`getEquipment()`, переменная в UI часто `machine`. Это всё одно и то же.
ТМЦ = товарно-материальные ценности.

**Осмотр** (`Scan`, в API — `fault_inspection`) — то, что обходчик отправляет по
итогам обхода: комментарий, фото, ссылка на задачу или проблему, приоритет.
Класс называется `Scan` («скан»), но семантически это **осмотр**, а не
результат сканирования QR. Отправляется на `/v1/company/fault_inspections/`.

**Задача** (`Task`) — единица работы по оборудованию. Статусы (`resultStatus`):
- `open` — назначенная конкретному человеку (`responsibleUser`);
- `scheduled` — запланированная по периодичности, адресована **роли**
  (`periodicTask.customRoles`);
- `closed` — закрытая.

Русские подписи — `tasksStatusLabels` (`tasks_filter_state.dart:6-10`).

**Периодическая задача** (`PeriodicTask`) — правило повторения: `periodicityRule`,
`nextDueAt`, `lastRunAt`, `customRoles`. Живёт внутри `Task.periodicTask`.

**`PeriodicTaskRequest`** — **не** то же самое, что `PeriodicTask`. Это тело
запроса на создание задачи (`POST /v1/company/periodic_task/`), которое приложение
кладёт в свою очередь. Используется для ad-hoc задач по проблеме «Другое»
(`params: {'target_type': 'ad_hoc', 'priority': ...}`).

**ТО** — техническое обслуживание. В коде распознаётся **по подстроке в русском
названии**: `periodicTitle.contains('Техническое обслуживание')`
(`data_provider.dart:132`). Такие задачи получают в `stringBox` метку
`maintenance_task_<uuid>` и не отправляются, пока не уйдёт наработка по тому же
оборудованию.

**Типовая проблема** (`TypicalProblem`, в API — `eq_fault`) — элемент справочника
неисправностей, привязанный к конкретному оборудованию. Два псевдоэлемента —
константы класса:
- `TypicalProblem.empty` (`id: -1`, «Нет проблем») — «проблемы нет»;
- `TypicalProblem.other` (`id: 0`, «Другое») — требует комментария **и**
  приоритета, порождает ad-hoc задачу.

**Неисправность** (`EquipmentFault`) — отдельная модель, приходит внутри `Task`.

**Наработка** (`UsageParameter` — параметр, `UsageUpdate` — обновление) —
показание счётчика оборудования: моточасы, километры, циклы. Единицы —
справочник `UsageUnit` (`/v1/company/equipment/usage-unit-types`). Обходчик
видит только те параметры, у которых `maintenanceRole.name` совпадает с его
`effectiveRole`.

**Состояние оборудования** (`EquipmentState`) — словарь `код → русское название`
(«В работе», «В ремонте», «В резерве», …). Приходит целиком одним объектом с
`/v1/company/equipment/states`. Меняется **сразу**, не через очередь.

**Инвентаризация** (`Session`) — сессия пересчёта, `status == 'active'`.
Отображается только в отладочной строке (`GlobalState.updateDebugInventory`).
Полноценного UI инвентаризации в приложении **нет** — экран удалён
(коммит `2c9cb69 … drop dead inventory screen`).

**Приоритет** (`Priority`) — `low` / `medium` / `high`, русские подписи в
`Strings.low/medium/high`, объекты — `Priorities.LOW/MEDIUM/HIGH`
(`lib/src/model/priority.dart`). Цвета в самой модели захардкожены
(`Colors.yellow/orange/red`), а семантические — в `AppSemanticColors`
(`cs.priorityLow/Medium/High`). Для UI используй вторые.

**Ремонт** (`Repair`, в API — `/v1/repairs`) — работа по оборудованию со своим
жизненным циклом: «Открыт» (`open`) → «На рассмотрении» (`under_review`) →
«Закрыт» (`closed`). Обходчик доводит ремонт до «На рассмотрении»; закрывает
его и списывает склад **администратор в веб-админке**. Не путать с `Task`:
задача — единица обхода, ремонт — отдельная сущность со складскими
последствиями.

**ЗИП** (`SparePart`, в API — `spare_parts`) — запасные части, инструменты и
принадлежности. В приложении справочник только для чтения.

**Фактический расход** (`RepairConsumption`, в API — `actual_consumptions`) —
сколько ЗИП реально израсходовано в ремонте. Заполняется обходчиком, **списание
происходит не в момент ввода**, а при закрытии ремонта администратором. Пустой
список = списания не будет.

**Норма расхода** (`ConsumptionNorm`, в API — `consumption_norms`) — плановый
состав ЗИП по оборудованию. Для ремонтов берутся только нормы с назначением
`repair`. Норма — справочный ориентир: сама по себе она ничего не списывает.

**Черновик ремонта** (`PendingRepair`) — ремонт, созданный без связи и лежащий
в очереди. У него нет серверного номера, в списке помечается «Черновик».
Его `localId` — одновременно ключ бокса и `Idempotency-Key`.

**Ответственный и должность** — у ремонта может быть конкретный исполнитель
(`responsible_user`), должность (`responsible_role`) или и то и другое.
Ремонт с должностью, но без исполнителя — **свободный**: его видит каждый
обходчик подходящей роли и может «взять в работу» (`claimRepair`).

**Идемпотентность** (`Idempotency-Key`) — заголовок, по которому сервер узнаёт
повторную отправку и возвращает уже созданную сущность вместо второй. На нём
держится офлайн-очередь ремонтов.

**Роль исполнителя** (`CustomRole` / `customRoleId` / `MaintenanceRole`) —
должность, к которой привязана периодическая задача или параметр наработки.
`User.customRoleId` (int) сопоставляется с `periodicTask.customRoles[].id`;
`User.effectiveRole` (string) — с `usageParameter.maintenanceRole.name`.
Две разные системы сопоставления, не перепутай.

## Технические термины проекта

**`GlobalState`** — статический класс-хаб (`lib/global_state.dart`): доступ к
`dataProvider`, текущему пользователю, времени в UTC, отладочной строке и
кэшированной проверке связи. Не путать с состоянием UI.

**`DataProvider`** — единственный «репозиторий»: владеет всеми Hive-боксами,
in-memory кэшем и синхронизацией. Разбит на part-файлы `_remote`, `_sync`,
`_outbox`.

**`Settings`** — статический класс пользовательских настроек поверх Hive
`stringBox` (`lib/settings.dart`). Не путать с экраном настроек уведомлений
(`NotificationSettings` — это модель серверных настроек).

**Outbox / очередь** — пара боксов `<X>Box` + `<X>PendingBox`. Запись
перекладывается в pending перед отправкой; при неуспехе возвращается обратно
через 120 секунд. Три очереди: осмотры, наработки, периодические задачи.

**`key()`** — метод модели, возвращающий md5 от JSON-содержимого. Используется
как ключ Hive для элементов очереди → дедупликация по содержимому.
Есть у `Scan`, `UsageUpdate`, `PeriodicTaskRequest`.

**`stringBox`** — Hive-бокс `strings` типа `Box<String>`. Универсальное
key-value хранилище: настройки, флаги онбординга, timestamp-ы очереди, метки ТО.
Для одиночных значений и флагов; коллекции сущностей живут в своих
типизированных боксах.

**`typeId`** — уникальный номер Hive-адаптера. Занято 0–4 и 6–28; `5` освобождён,
но переиспользованию не подлежит. Следующий свободный — 29.

**`simulateOffline`** — статический рубильник `API.simulateOffline`
(`api.dart:61`) для ручного тестирования офлайна: `isAlive()` → `false`,
остальные методы бросают `SocketException`.

**`hasConnectionToServer`** — геттер `GlobalState`, который **не** проверяет
состояние сети, а пингует `GET {baseUrl}/docs` с таймаутом 5 с и кэширует
результат на 10 секунд.

**`mainSync()`** — полная синхронизация всех справочников. Не путать с
`syncScans()` (отправка очереди) и `syncDataAndScans()` (кнопка «Синхронизировать
данные», возвращает `SyncResult`).

**`backOr(fallback)`** — extension на `GoRouter`: `pop()` на предыдущий экран,
а если стек пуст — сброс на запасной адрес. Стандартный способ реализовать
кнопку «назад». Пустой стек штатен: на экран попадают тапом по
пуш-уведомлению или сразу после сброса.

**`clearStackAndNavigate(path)`** — extension на `GoRouter`
(`utils/go_router_ext.dart`): `pop()` до дна + `pushReplacement`. Только для
сбросов — вход, выход, splash, онбординг. Для переходов вглубь — `push`.

**`MyAppBar`** — не виджет, а класс со **статическим** методом
`build(BuildContext)`, возвращающим `AppBar` в зависимости от текущего
`location`. Экраны вызывают его как `MyAppBar.build(context) as AppBar`.

**`AnyController<T>`** — обобщённая обёртка над `ValueNotifier<T?>` для значений
формы (`utils/any_controller.dart`).

**`ControllerListenerMixin`** — миксин на `State`, автоматически
подписывающийся/отписывающийся от `controllerListenable`.

**`Dependent<T>`** — обёртка над `ValueListenableProvider` + `Consumer`
(`utils/dependent.dart`). Один потребитель. Для нового кода — обычный
`ValueListenableBuilder`.

**`AppThemeId`** — `fresh` (лаймовый зелёный, дефолт) и `industrial`
(графит + cyan). В UI подписаны «Свежая» и «Графит».

**`AppSemanticColors`** — extension на `ColorScheme` с ролями `success`,
`warning`, `info`, `priorityHigh/Medium/Low`.

**Демо-оборудование** (`DemoEquipment.conveyorBelt`, uuid
`'demo-onboarding-conveyor'`) — фиктивная «конвейерная лента» для онбординга.
Этот uuid специально распознаётся в `getTasksForMachine`, `_onStateChanged` и
`_submit`.

**Отладочная полоса** — постоянная строка внизу каждого экрана
(`Сервер: доступен | Осмотров не отправлено: N | Пользователь: X`). Часть
продукта, а не временный дебаг.

## Аббревиатуры

| Сокращение | Расшифровка |
|---|---|
| ТОиР | Техническое обслуживание и ремонт |
| ТО | Техническое обслуживание |
| ППР | Планово-предупредительный ремонт (термин бэкенда, в мобилке не используется) |
| ТМЦ | Товарно-материальные ценности |
| ЗИП | Запасные части, инструменты и принадлежности |
| S/N | Serial number, серийный номер |
| SSE | Server-Sent Events — односторонний поток событий от сервера |
| 1С | Учётная система заказчика; интегрируется с **бэкендом**, мобилка о ней не знает |

## Легко перепутать

| Пара | Разница |
|---|---|
| `Scan` ↔ сканирование QR | `Scan` — это **осмотр**, отправляемая запись. Сканирование QR — `mobile_scanner` в `qr_screen.dart` |
| `InventoryRecord` ↔ `Session` | Первое — оборудование, второе — сессия инвентаризации |
| `PeriodicTask` ↔ `PeriodicTaskRequest` | Первое — данные с сервера внутри `Task`, второе — тело запроса на создание |
| `NotificationSettings` ↔ `Settings` | Первое — серверные настройки уведомлений (модель), второе — локальные настройки приложения (статики) |
| `NotificationsService` ↔ `PushNotificationsController` | Первое — список и SSE в основном изоляте, второе — управление Android-foreground-сервисом |
| `notification_router.dart` ↔ `go_router` | Первое — обработка тапа по пушу, а не маршрутизация приложения |
| `customRoleId` (int) ↔ `effectiveRole` (String) | Разные механизмы сопоставления: задачи по `id`, наработка по `name` |
| `skip` ↔ `offset` | В URL всегда `skip`, в сигнатуре Dart-метода — `offset` |
| `lib/src/design/README.md` ↔ документация проекта | Это боилерплейт генератора тем, к проекту отношения не имеет |
| `Task` ↔ `Repair` | Задача — единица обхода. Ремонт — отдельная сущность со складскими последствиями и своим жизненным циклом |
| `Repair` ↔ `PendingRepair` | Первое — ремонт, известный серверу. Второе — черновик в очереди, серверного номера ещё нет |
| Норма расхода ↔ фактический расход | Норма — план, справочный ориентир. Факт вводит обходчик, и списывается именно он |
| «Отправить» (ремонт) ↔ отправка очереди | Первое — перевод ремонта в «На рассмотрении». Второе — выгрузка накопленного из Hive на сервер |
| Закрыть ремонт ↔ отправить на рассмотрение | Закрывает только администратор в веб-админке; в приложении такого действия нет |
| `responsible_user` ↔ `responsible_role` | Исполнитель ↔ должность. Ремонт с должностью без исполнителя — свободный, его можно «взять в работу» |
